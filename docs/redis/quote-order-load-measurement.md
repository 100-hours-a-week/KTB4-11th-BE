# 시세 전달·주문 처리 부하 측정 — 2026-10-12

최신 결과: 가격 미충족 주문 선검사에 이어 대기 주문의 보고서 반복 조회를 제거했다. 같은 조건에서 미충족 단계는 0.908초, 체결 단계는 3.459초이며 관련 테스트 26개가 통과했다. 아래 표는 변경 단계별 기록이며 최신 상세는 마지막 절에 기록한다.

## 구성과 범위

담당 BE 1대와 일반 BE 2대를 별도 Java 21 JVM으로 실행했다. 실제 로컬 Valkey(6380), 각 BE의 운영 Spring 구성·Redis 저장·개별 채널 Pub/Sub·주문 체결 서비스를 사용한다. DB는 테스트마다 새로 만드는 공유 H2 TCP DB이며 키움 REST와 WebSocket은 가짜 응답이다. 실제 증권사 주문을 보내지 않는다.

한 계좌에 초기 현금 20,000,000원을 설정하고 `TST009`의 지정가 매수 주문 100개를 저장했다. 주문마다 1주, 지정가 120,000원이다. 체결 후에도 구독을 유지하고 뒤따르는 알림을 검증하기 위해 지정가 1원인 대기 주문 1개를 추가했다. 주문 생성 HTTP의 부하는 포함하지 않으며 테스트 준비 과정에서 repository로 저장한다.

1. 200,000원 시세 20개를 연속 저장·발행한다. 매수 조건에 맞지 않으므로 101개 주문과 현금을 유지해야 한다.
2. 119,500원 시세 20개를 연속 저장·발행한다. 같은 종목의 알림을 여러 BE가 처리해도 대상 주문 100개가 각각 한 번만 체결돼야 한다.

측정 시간은 발행 시작부터 두 일반 BE의 수신 확인 및 해당 단계의 DB 결과 확인까지다. 개별 메시지 지연의 p95나 순수 Redis 전송 시간은 아니다. 일반 BE의 테스트 수신 기록은 운영 주문 리스너보다 먼저 실행되므로, 마지막 알림의 모든 내부 작업 완료까지 측정한 값이라고 해석하지 않는다.

## 결과

부하 테스트 1개가 통과했다. 운영 코드 변경 없이 테스트와 문서를 추가했다.

| 확인 항목 | 결과 |
|---|---|
| 시세 발행 | 총 40개, 두 단계에 각각 20개 |
| 일반 BE 수신 | 두 서버 각각 40개 |
| 매수 조건 미충족 단계 | 대기 101개, 체결 0개, 현금 20,000,000원 |
| 매수 조건 충족 단계 | 체결 100건, 서로 다른 주문 ID 100개 |
| 보유 수량 | 100주 |
| 최종 현금 | 8,050,000원 = 20,000,000 − 119,500 × 100 |
| 남은 대기 주문 | 지정가 1원인 검증용 주문 1개 |
| 담당 활동 | 부하 후에도 유지 |
| 조건 미충족 단계 경과 시간 | 34.161초 |
| 체결 단계 경과 시간 | 11.038초 |

40개 알림의 중복 체결 방지는 확인했지만 실시간 처리 속도가 충분하다고 판단할 결과는 아니다. 코드상 현재 가격 조건을 충족하지 않는 주문도 `OrderExecutionService.executeLimit`에 들어가 계좌 잠금·주문 조회를 수행한 뒤 가격 조건을 확인한다. 같은 계좌의 주문 100개와 여러 BE의 반복 판단은 DB 잠금 경합과 조회 부하를 만든다. 이번 측정만으로 전체 지연 중 각 원인의 비중까지 확정하지 않았으며, 이 경로는 후속 성능 개선 검토 대상이다.

테스트는 단일 종목·단일 계좌의 제한된 부하다. 200개 종목, callback 큐 포화(256개), 장시간 연속 시세, 호가 처리, 여러 계좌 부하, 실제 MySQL 잠금·배포 Valkey ACL/TLS·실제 키움과 BE 세 개를 결합한 검증은 포함하지 않는다. Pub/Sub의 운영 메시지 무손실 전달을 보장하는 시험도 아니다. 이전 REST 대기 부하는 [별도 측정](rest-load-measurement.md)에 기록한다.

## 재현과 정리

로컬 Valkey가 실행 중이어야 한다. 같은 저장소에서 다른 담당 BE나 활동 키를 사용하는 테스트를 동시에 실행하지 않는다.

```powershell
$env:REDIS_LIVE_TEST = 'true'
$env:REDIS_LOAD_TEST = 'true'
.\gradlew.bat test --tests '*MultiProcessRedisLiveTests.burstQuotesExecuteOneHundredOrdersOnceAcrossThreeProcesses'
Remove-Item Env:REDIS_LIVE_TEST
Remove-Item Env:REDIS_LOAD_TEST
```

결과 JSON은 `build/reports/redis-order-load.json`에 생성된다. 기본 테스트에서는 이 부하 조건을 건너뛴다. 기존 담당 활동 키나 `TST009`의 테스트 캐시가 있으면 덮어쓰지 않고 실패한다. 테스트 종료 시 자식 BE, 임시 H2 DB, 자신이 만든 시세 키를 정리하고 담당 활동 종료를 확인한다. 실제 키움 토큰 키는 사용하거나 삭제하지 않는다.

## 가격 조건 선검사 후 재측정

`OrderExecutionListener.attempt`에서 유효한 양수 가격이 매수 지정가보다 높거나 매도 지정가보다 낮으면 체결 서비스 진입 전에 제외한다. 따라서 해당 주문의 반복 시세 출처 확인·자산 평가·체결 트랜잭션·계좌 잠금을 생략한다. Redis 알림의 시세 출처 확인과 종목별 대기 주문 조회는 유지한다. 가격이 지정가와 같으면 기존 체결 경로를 사용한다. 가격 조건이 맞는 주문의 잠금 이후 상태·가격·장 운영시간·시세 출처 재검증은 변경하지 않았다.

만료 규칙은 그대로이며 미충족 주문은 기존 `OrderSubscriptionService.refresh`의 5초 갱신 주기에서 취소·구독 정리를 한다. 이전에는 미충족 시세를 처리하면서도 체결 서비스 안에서 만료 주문을 취소할 수 있었으나, 이 경로를 생략하므로 미충족 시세마다 즉시 만료 취소하지 않는다. 주문 접수 직후의 `finally` 구독 갱신은 유지한다. 주기 작업이나 DB가 지연되면 5초 안에 정리가 끝난다고 보장하지 않는다.

| 단계 | 개선 전 | 개선 후 |
|---|---|---|
| 가격 조건 미충족 시세 20개 | 34.161초 | 6.746초 |
| 가격 조건 충족 시세 20개·주문 100개 | 11.038초 | 14.908초 |

두 일반 BE는 다시 각각 40개 알림을 받았으며, 서로 다른 주문 100개의 체결 100건·보유 100주·현금 8,050,000원·검증용 대기 주문 1개·담당 활동 유지가 확인됐다. 이번 실행의 미충족 단계는 약 80% 단축됐지만 체결 단계는 더 오래 걸렸다. 로컬 단일 실행 간 비교이므로 개선율을 운영 처리량으로 일반화하지 않으며, 체결 성능이 개선됐다고 판단하지 않는다. 전체 시세 처리 지연이 해소된 것도 아니다.

새 테스트 2개는 변경 전 미충족 매수·매도 주문도 체결 서비스를 호출하여 실패하는 것을 확인했다. 변경 후 미충족 요청의 체결·평가 호출 생략, 매수·매도 조건 충족 및 지정가와 동일한 가격에서의 기존 체결 경로를 검증한다. 시세 출처·체결 롤백·중복 체결·장 마감 취소·전일 주문 정리·구독 갱신 및 다중 BE 부하를 포함한 관련 테스트 25개가 통과했다(실패·오류·건너뜀 0건). 전체 테스트, 실제 키움, MySQL, 배포 Valkey 검증을 이번 단계에서 재실행하지 않았다.

## 연결된 보고서의 반복 조회 제거 후 재측정

Hibernate 통계로 보고서가 있는 주문과 없는 주문을 섞은 20개를 실제 조회했다. 기존 `findPendingForPrice`는 주문 목록 조회 외에 연결된 `AiOrderReport`의 존재 여부를 주문마다 조회하여 SQL 21회를 실행했다. `Order.report`의 역방향 선택적 일대일 관계에서 `LAZY` 표시만으로 추가 조회를 방지하지 못한 것이다. 이 추가 SQL 횟수가 2회 이하이어야 한다는 회귀 테스트는 기존 코드에서 실패했다.

해당 목록 조회에 `left join fetch o.report`를 추가해 계좌·주문·보고서를 함께 읽는다. 보고서 없는 주문도 유지되며 주문의 상태·수량·가격·시각 및 계좌 잠금 이후의 체결 재검증은 변경하지 않는다. Redis 키·TTL·구독 정책도 변경하지 않았다. 회귀 테스트는 주문 20개와 보고서 10개의 조회 결과 및 SQL 횟수 상한을 함께 검증하며 변경 후 통과했다.

| 단계 | 가격 선검사 후 | 보고서 반복 조회 제거 후 |
|---|---|---|
| 가격 미충족 시세 20개 | 6.746초 | 0.908초 |
| 가격 충족 시세 20개·주문 100개 | 14.908초 | 3.459초 |

두 일반 BE는 각각 시세 알림 40개를 수신했다. 서로 다른 주문 100개가 각각 한 번 체결됐으며 현금 8,050,000원·보유 100주·검증용 대기 주문 1개·담당 활동 유지가 확인됐다. 관련 회귀 및 부하 테스트 26개가 모두 통과했다(실패·오류·건너뜀 0건). 측정 방식과 검증 범위는 앞과 동일하며, SQL 반복의 원인은 실제 통계로 확인했지만 단계 경과 시간의 개선율은 한 번씩의 로컬 실행 비교다. 운영 처리량이나 실제 MySQL의 성능으로 일반화하지 않는다.

실제 체결 시 필요한 계좌 잠금·자산 변경 트랜잭션은 유지된다. 여러 BE의 체결 경쟁을 단일 BE로 모으거나 알림을 합치는 정책은 추가하지 않았다. 전체 회귀 및 실제 MySQL·배포 Valkey 검증은 별도다.

## 후속 전체 회귀 실행

로컬 Valkey·REST 부하·시세 주문 부하를 모두 켠 전체 테스트는 282개 중 276개 통과, 실제 키움 연결 테스트 6개 건너뜀, 실패·오류 0건이었다. 같은 주문 부하의 반복 실행에서 미충족 단계 0.767초·체결 단계 3.548초였으며 두 일반 BE의 각각 40개 수신·주문별 체결 1회·보유 100주·현금 8,050,000원·담당 활동을 다시 확인했다. 이전 별도 실행 수치는 위에 보존한다. 실제 MySQL·배포 Valkey 결과가 아니며 세부 실행 설정은 [배포 준비 문서](redis-deployment-checklist.md)에 기록한다.
