# REST 대기 부하 측정 — 2026-10-12

최신 상태: 사용자 승인으로 호출 순서 대기 상한 3초를 적용했다. 마지막 절에 적용 후 측정 결과를 기록한다. 앞의 표와 설명은 변경 단계별 기록이다.

아래 수치는 응답 후 220ms 방식의 이전 측정 기록이다. 이후 개별 TR의 최근 1초 최대 5회까지 즉시 전송하고 초과 요청만 기다리도록 변경했으며 새 결과는 문서 하단에 기록한다.

사용자 확인에 따라 현재 연결 3초·응답 5초와 TR별 응답 완료 후 220ms 간격을 유지한 채 측정했다. 별도 TR 대기 상한은 아직 추가하지 않았다. 현재가도 기존 담당·구독·연결 ID 검증을 유지하며 추가 경과시간 제한은 추후 결정한다.

## 측정 범위

로컬 가짜 외부 HTTP API와 실제 `DirectKiwoomRestTransport`, `CollectorQueryController`, 일반 BE의 `RemoteKiwoomRestTransport` 및 기존 HTTP 제한시간을 사용했다. 조회 TR은 ka10001과 ka10100이며 요청을 동시에 출발시켰다. 서버·클라이언트는 기본 Tomcat처럼 플랫폼 스레드로 실행했다.

Redis 담당 확인·토큰 발급은 테스트 대역이다. 실제 키움·배포 Valkey·전체 Spring/Tomcat 구성·DB·시세 Pub/Sub·주문 체결의 부하를 측정한 결과가 아니다. 이 수치를 운영 서버 처리 용량으로 해석하지 않는다.

## 결과

| 동시 요청 | TR 수 | 가짜 외부 응답 지연 | 성공 / 실패 | 응답 p50 | 응답 p95 | 담당 전체 처리 완료 |
|---|---|---|---|---|---|---|
| 5개 | 1개 | 100ms | 5 / 0 | 1.064초 | 1.714초 | 1.759초 |
| 20개 | 1개 | 100ms | 14 / 6 | 3.257초 | 5.006초 | 6.780초 |
| 20개 | 2개, 각 10개 | 100ms | 20 / 0 | 1.498초 | 3.256초 | 3.257초 |
| 10개 | 1개 | 1,000ms | 4 / 6 | 5.016초 | 5.019초 | 12.302초 |

p50은 요청 절반, p95는 요청 95%가 이 시간 안에 성공 또는 실패 응답을 받았다는 뜻이다. 실패는 일반 BE의 응답 제한시간 초과이며 실패도 응답시간 통계에 포함한다. 한 번의 로컬 측정 결과로 반복 측정·실제 환경 검증이 필요하다.

같은 TR의 외부 호출 시작 간격은 100ms 응답에서 최소 324~325ms, 1,000ms 응답에서 최소 1,243ms였다. 응답 완료 뒤 220ms를 두므로 현재 구현의 처리 속도는 외부 응답 시간에도 영향을 받는다. 두 TR은 별도 제한으로 진행됐다.

## 확인한 의미와 남은 결정

- 같은 TR 요청이 몰리면 순서 대기 때문에 일반 BE가 5초를 넘겨 실패할 수 있다.
- 호출자의 시간 초과가 담당의 대기·시작된 조회를 취소하지 않는다. 20개 단일 TR은 호출자들이 약 5.021초에 응답을 마친 뒤 담당이 6.780초까지 20개 모두 처리했다. 느린 응답의 10개 요청도 12.302초까지 모두 처리했다.
- 따라서 대기 허용 시간·대기 요청 수·실패 처리 정책은 측정 결과를 바탕으로 별도 확인받아야 한다. 이번 단계는 정책이나 운영 코드를 변경하지 않았다.
- 이 측정은 실제 증권사 한도 검증을 대신하지 않는다. 공식 TR별·그룹/전체 유량 제한은 여전히 확인 대상이다.

## 재현

```powershell
$env:REST_LOAD_TEST = 'true'
.\gradlew.bat test --tests '*CollectorRestLoadTests'
Remove-Item Env:REST_LOAD_TEST
```

결과 JSON은 `build/reports/redis-rest-load.json`에 생성된다. 기본 테스트에서는 건너뛴다. 키움 인증 정보와 실제 Redis 연결은 필요하지 않다. 로컬 HTTP 서버와 실행 스레드는 종료 시 정리한다.

## 초과 요청만 대기하도록 변경한 뒤 재측정

사용자가 제공한 공식 FAQ의 TR당·토큰별 실전 초당 5회 기준으로, 현재 단일 계좌/토큰의 개별 api-id에 최근 1초 최대 5회를 허용한다. HTTP 응답을 기다리는 동안 제한 잠금을 유지하지 않는다. 실패·토큰 재시도도 한 건으로 세고 갱신 때 같은 계좌의 카운터를 초기화하지 않는다.

| 동시 요청 | TR 수 | 외부 응답 지연 | 성공 / 실패 | 응답 p50 | 응답 p95 | 전체 처리 완료 |
|---|---|---|---|---|---|---|
| 5개 | 1개 | 100ms | 5 / 0 | 0.227초 | 0.228초 | 0.231초 |
| 20개 | 1개 | 100ms | 20 / 0 | 1.143초 | 3.166초 | 3.169초 |
| 20개 | 2개, 각 10개 | 100ms | 20 / 0 | 0.152초 | 1.151초 | 1.156초 |
| 10개 | 1개 | 1,000ms | 10 / 0 | 1.029초 | 2.034초 | 2.035초 |

같은 네 조건에서 기존 시간 초과가 없어졌다. 더 많은 요청이나 실제 외부 지연에서는 여전히 5초 응답 제한을 초과할 수 있다. 별도 대기 상한·취소 정책은 추가하지 않았다. 요청 시작 허용 시각 기준의 여러 최근 1초 창 검증, 첫 5개 동시 진행·6번째 대기·다른 TR 독립 처리, 토큰 값 변경 후 8005 재시도 제한 유지 테스트가 통과했다. 네트워크 수신 시각과 허용 시각은 같지 않으므로 서버 수신 간 최소 간격만으로 한도를 판정하지 않는다.

Valkey 및 부하 테스트를 함께 켠 전체 검증: 277개 중 271개 통과, 실제 외부 연결 테스트 6개 건너뜀, 실패·오류 0건. 실제 키움에 이 부하를 보내지 않았다. 다중 프로세스 테스트의 장중 고정 시계는 서버 초기화 때 적용하도록 보완했으며, 테스트 실패 때도 활동 키의 정리를 기다려 다음 테스트에 남기지 않는다.

## 최대 100개 동시 요청 추가 측정

같은 운영 설정으로 기존 네 조건과 아래 네 조건을 함께 실행했다. `CollectorRestLoadTests` 1개 테스트의 8개 측정 조건이 통과했다. 운영 코드는 변경하지 않았다. 테스트 실행 스레드는 동시 요청 수에 맞춰 늘려 로컬 가짜 서버의 스레드 부족 영향을 줄였다.

| 동시 요청 | TR 수 | 외부 응답 지연 | 성공 / 시간 초과 | 응답 p95 | 담당 전체 처리 완료 |
|---|---|---|---|---|---|
| 30개 | 1개 | 100ms | 25 / 5 | 5.031초 | 5.269초 |
| 50개 | 1개 | 100ms | 25 / 25 | 5.038초 | 9.362초 |
| 100개 | 1개 | 100ms | 25 / 75 | 5.163초 | 19.542초 |
| 30개 | 1개 | 1,000ms | 20 / 10 | 5.038초 | 6.181초 |

이번 실행에서도 기존 네 조건은 모두 성공했다. 20개 단일 TR·100ms는 p95 3.238초, 두 TR에 각 10개·100ms는 1.224초, 10개 단일 TR·1,000ms는 2.074초였다. 반복 실행의 수치는 초기화와 로컬 실행 환경에 따라 달라지며 위의 이전 측정과 별도 기록이다.

100개 조건에서 일반 BE는 약 5.197초에 모든 성공/실패 응답을 받았지만, 담당은 그 시점에 25개만 완료했고 이후에도 나머지를 호출해 최종 100개를 모두 완료했다. 호출자 시간 초과가 담당의 대기 요청을 취소하지 않는 문제가 부하가 커질수록 커진다. 느린 응답 조건에서는 기다리는 시간 외에 외부 응답 시간도 필요하므로 성공 가능한 요청 수가 더 줄었다.

다음 정책은 사용자 확인 후 적용한다. 담당의 호출 순서 대기 상한을 두어 오래 기다린 요청을 외부 호출 전에 실패시키는 방안을 우선 검토한다. 대기 상한만으로 전체 응답시간을 보장할 수는 없으며, 이미 시작된 외부 조회의 응답 제한과 호출자 시간 초과 후 취소 처리는 별도 사항이다. 아직 대기 상한·대기 개수 제한·취소 정책을 추가하지 않았다. 실제 키움, Valkey, DB, Pub/Sub 및 주문 체결 부하 검증은 이번 측정 범위에 포함하지 않는다.

## 사용자 승인 후 3초 대기 상한 적용

담당의 TR 호출 순서 대기를 외부 호출 시도마다 최대 3초로 제한했다. 대기 시작은 한도 잠금을 획득하기 전이며, 반복 확인할 때 만료를 검사하고 가장 오래된 호출 기록의 만료 시각과 대기 상한 중 더 짧은 시간만 기다린다. 만료된 요청은 외부 호출 횟수에 포함하지 않고 실패한다. 내부 조회 API의 기존 예외 처리로 503을 반환한다. 토큰 확보 시간·외부 HTTP 응답 시간은 이 상한 밖이며, 8005 재시도는 별도의 대기 상한을 가진다. 연결 3초·응답 5초 설정은 변경하지 않았다.

| 동시 요청 | TR 수 | 외부 응답 지연 | 성공 / 호출 전 거절 | 응답 p95 | 담당 전체 처리 완료 |
|---|---|---|---|---|---|
| 5개 | 1개 | 100ms | 5 / 0 | 0.191초 | 0.194초 |
| 20개 | 1개 | 100ms | 20 / 0 | 3.139초 | 3.145초 |
| 20개 | 2개, 각 10개 | 100ms | 20 / 0 | 1.135초 | 1.143초 |
| 10개 | 1개 | 1,000ms | 10 / 0 | 2.035초 | 2.040초 |
| 30개 | 1개 | 100ms | 20 / 10 | 3.130초 | 3.138초 |
| 50개 | 1개 | 100ms | 20 / 30 | 3.161초 | 3.169초 |
| 100개 | 1개 | 100ms | 20 / 80 | 3.095초 | 3.162초 |
| 30개 | 1개 | 1,000ms | 19 / 11 | 4.039초 | 4.053초 |

이번 실행에서 실패한 요청은 모두 외부 호출 전에 거절됐다. 100개 조건의 외부 호출은 최종 20개로 끝나며, 이전처럼 호출자가 실패한 뒤 나머지 80개를 계속 호출하지 않았다. 느린 응답 조건은 대기를 통과한 요청이 외부 응답을 기다리므로 약 4초가 걸렸다. 3초 근처에서 허용되는 개수는 요청 도착·스레드 배정 시각에 따라 달라지므로 특정 동시 요청 수까지 항상 성공한다고 보장하지 않는다.

새 회귀 테스트는 기존 코드에서 30개 요청이 모두 호출돼 실패하는 것을 먼저 확인한 뒤, 3초 만료 실패와 성공한 요청만 외부로 호출되는지를 검증했다. 최근 1초 창, 다른 TR의 독립 진행, 토큰 재시도 한도 유지와 함께 관련 테스트 17개가 모두 통과했다(부하 테스트 1개에 8개 조건 포함). 이번에는 전체 테스트 및 실제 키움·배포 Valkey 부하 검증을 재실행하지 않았다. 대기 개수 제한과 이미 시작된 외부 요청의 취소 정책은 추가하지 않았다.

## 후속 전체 회귀 실행

전체 회귀에 이 부하 시험을 포함하여 282개 중 276개 통과, 실제 키움 연결 테스트 6개 건너뜀, 실패·오류 0건이었다. REST 8개 조건의 실패 요청은 모두 호출 전 거절이었으며 외부 완료 건수와 거절 건수의 합이 요청 수와 같았다. 이번 동일 TR·100ms 조건의 성공/거절은 20개 요청에서 16/4, 30개에서 20/10, 50개에서 19/31, 100개에서 20/80이었다. 100개 조건은 약 3.214초에 끝났으며 거절한 요청을 뒤늦게 외부 호출하지 않았다. 두 TR에 각 10개 및 동일 TR 10개·1,000ms 조건은 모두 성공했다.

3초 근처의 요청 도착·스레드 배정 차이로 성공 수가 달라지는 점을 다시 확인했다. 동시 20개를 항상 모두 처리하는 보장이 아니며, 호출 전 거절은 승인된 대기 상한 정책에 따른 동작이다. 실제 키움에는 부하를 보내지 않았으며 [전체 검증 기록](redis-deployment-checklist.md)을 참고한다.
