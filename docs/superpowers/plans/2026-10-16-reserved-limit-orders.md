# 지정가 예약 주문 Implementation Plan

> 구현 시 executing-plans 스킬을 사용하고 각 단계의 실패 테스트 → 변경 → 통과 확인 순서로 진행한다.

**Goal:** 지정가 주문을 시간 제한 없이 접수하고, 체결 또는 사용자 취소까지 유지하며 거래 시간에만 체결한다.

**Architecture:** 기존 Order의 PENDING 상태와 예약 금액·수량 계산을 재사용한다. 주문 접수의 성공 조건에서 실시간 시세 연결을 분리하고, 체결 트랜잭션에서 거래 시간과 시세 유효성을 검사한다. 별도 체결 서버는 만들지 않는다.

**Tech Stack:** 기존 Spring Boot/JPA/MySQL/Redis.

**Spec:** 이 문서의 확정 정책 및 2026-10-16 사용자 요청.

## 기준과 범위

- 구현 브랜치: feat/130-reserved-limit-orders (초기 조사: feat/127-competition/daily-performance). 기존 대회 관련 주문·체결 제한을 보존한다.
- 시장가 주문 차단, 지정가 주문 상시 접수, 한국 시간 09:00 이상 15:30 미만에만 체결.
- 날짜 변경·장 마감으로 주문을 취소하지 않는다. 사용자 취소 또는 체결까지 PENDING 유지.
- 장외에 접수한 예약 주문은 다음 거래일 장중에 새로 수신한 시세 이벤트로 지정가 조건을 비교한다. 장 시작만을 이유로 과거 Redis 저장값을 조회하거나 REST로 보충해 예약 주문을 체결하지 않는다.
- 최신 시세는 BE 인메모리 캐시가 아니라 Redis에 저장된다. 기존 BE 저장 TTL 1일이 정상 적용된다면 금요일 값은 월요일까지 남지 않는다. TTL을 거래일 유효성 판단의 대체 수단으로 사용하지 않으며 AI 서버의 저장 정책과 혼동하지 않는다.
- 예약은 미래의 특정 시각을 지정하는 기능이 아니라, 거래 가능 시점까지 기다리는 지정가 주문이다.
- 기존 인증, 계좌 권한, 종목·호가 단위, 예약 현금·수량 검증을 유지한다.
- 새 주문 상태·테이블·예약 시간 컬럼은 필요하지 않다. 실제 스키마 변경 없이 구현하는 계획이다.
- AI 시세 서버 연동 규격 변경은 별도 작업이다.
- 사용자 결정: 공휴일·임시 휴장일 달력 연동은 별도 작업이다. 이번에는 주말·시간 제한과 당일 장중 실시간 시세를 사용한다.
- 대회 종료·계좌 비활성화의 기존 정책은 일반 장 마감 취소 제거와 구분한다. 기존 제한을 임의로 해제하지 않는다.

## 확인한 현재 코드

- OrderMarketValidator.validateLimit → validateMarket에서 접수 시간을 제한한다.
- OrderService.cancelExpiredPendingOrders는 장 마감 또는 전날 주문을 취소하며 OrderSubscriptionService.refresh가 5초마다 호출한다.
- OrderExecutionService.executeLimit도 전날 주문 또는 15:30 이후 주문을 취소한다.
- OrderController는 시장가 처리 경로를 여전히 제공한다.
- OrderSubscriptionService는 접수 중 구독 확보와 DB 저장을 연결한다. 장외 시세 서버 중단이 예약 접수 실패로 이어지지 않도록 변경해야 한다.
- OrderExecutionListener.orderCreated는 최신 시세 또는 REST 현재가로 최초 판단한다. 장외에는 이 조회와 판단을 생략한다.

## 작업 단계

### 1. 지정가 상시 접수

대상: order/controller/OrderController.java, order/validator/OrderMarketValidator.java 및 각 테스트.

- [x] 시장가 요청 거절, 08:59·15:30·야간 지정가 접수, 잘못된 종목·가격 거절 테스트를 먼저 작성한다.
- [x] 시장가를 명시적으로 거절하고 지정가 종목 검증에서 접수 시간 제한을 제거한다.
- [x] DB 주문 저장 성공이 시세 구독 성공에 의존하지 않게 OrderSubscriptionService.create와 호출 경로를 정리한다. 종목정보 검증 실패와 실시간 연결 실패는 구분한다.
- [x] 구독 실패 시에도 저장된 PENDING 주문과 자산 예약은 유지하고 이후 재시도한다. 접수 성공 이후의 알림 실패를 주문 실패로 응답하지 않는다.
- [x] 시세 연결 중단 상태에서 접수 가능한지, 잔액·매도 수량 초과는 여전히 거절되는지 검증한다.

### 2. 자동 만료 제거와 예약 유지

대상: order/service/OrderService.java, OrderSubscriptionService.java, execution/service/OrderExecutionService.java 및 관련 테스트.

- [x] 15:30 경과·날짜 변경·재시작 후 PENDING 유지 테스트를 추가한다.
- [x] cancelExpiredPendingOrders 및 주기 호출을 제거한다. 구독 복구/갱신 자체는 유지한다.
- [x] executeLimit의 날짜/마감 취소를 제거하고 거래 불가능 시 상태 변경 없이 반환한다.
- [x] 예약 금액·매도 수량이 다음 날에도 유지되고 취소 시 계산에서 제외되는지 검증한다.

### 3. 체결 시간과 시세 유효성

대상: execution/service/OrderExecutionService.java, execution/listener/OrderExecutionListener.java, market의 기존 시세 검증 경로.

- [x] 거래 시간 정책을 공통으로 사용하고 트랜잭션의 최종 자산 변경 직전에 시간을 재확인한다. 계좌 락 대기 중 15:30이 된 요청도 체결하지 않는다.
- [x] 주말을 차단하고 당일 장중 실시간 시세 여부를 검사한다. 공휴일·임시 휴장일 달력 연동은 사용자 결정에 따라 별도 작업으로 둔다.
- [x] 장외 최초 시세 조회·체결 판단을 생략한다. 다음 거래일 장중의 새 시세 이벤트를 받으면 DB의 기존 PENDING 주문과 비교한다. 이벤트가 없으면 주문은 계속 대기한다.
- [x] 장중 신규 주문의 최초 판단처럼 Redis 저장값을 조회하는 경로는 예약 주문의 다음 거래일 이벤트 처리와 구분한다. 저장값을 사용한다면 당일 장중 시세인지와 기존 출처 유효성을 검증한다.
- [x] 전일 시세를 오늘 수신된 것처럼 사용하는 경로, 지연 이벤트, 장외 REST 대체 조회가 체결에 쓰이지 않도록 검증한다.
- [x] 기존 연결/출처 검증은 유지한다. 현재가에 새로운 초 단위 만료 기준은 추가하지 않는다(이전 정책 유지).
- [x] 08:59:59 / 09:00:00 / 15:29:59 / 15:30:00, 전일 시세, 대회 거래 제한 테스트를 수행한다.

### 4. 복구와 다중 BE

대상: OrderSubscriptionService, RedisMarketStream, OrderExecutionListener 및 관련 통합 테스트.

- [x] DB의 모든 PENDING 주문이 생성 날짜와 무관하게 시작 시/재연결 시 구독 복구 대상인지 확인한다.
- [x] 예약 주문은 구독 복구 후 새 시세 이벤트로 판단을 재개한다. RedisMarketStream의 구독 시 저장 스냅샷 재발행 경로를 확인하여 과거 저장값이 새 이벤트로 취급되어 예약 주문을 체결하지 않도록 구분한다.
- [x] 금요일·주말 접수 → 월요일 개장 직후 새 이벤트 없음: PENDING 유지 → 월요일 유효 시세 수신: 조건 충족 시 체결 순서를 테스트한다. 전일 이벤트 지연 전달 및 저장 스냅샷 재발행으로는 체결되지 않는지도 검증한다.
- [x] 같은 시세를 여러 BE가 처리해도 기존 계좌 DB 락과 PENDING 재확인으로 한 번만 체결되는지 검증한다.
- [x] 취소와 체결 경합에서도 예약/잔액/보유 수량이 일관적인지 검증한다. FIFO 보장은 추가하지 않는다.

### 5. 문서와 최종 검증

- [x] 기존 주문/체결 설명의 당일 만료와 접수 시간 제한을 새 정책으로 수정한다.
- [x] 관련 주문·체결 테스트 후 전체 build를 수행한다. 외부 환경이 필요한 테스트의 건너뜀을 구분해 보고한다.
- [x] 로컬 DB/Redis 통합 검증 가능 여부를 확인하고 장외 접수 → 다음 거래일 체결 흐름을 고정 Clock으로 검증한다.
- [x] FE/AI 팀에는 지정가 상시 접수, 시장가 거절, 무기한 대기와 예약 자산 유지 정책을 인계한다. 외부 메시지는 별도 사용자 지시가 있을 때만 전송한다.

## 완료 기준

구현·검증 기록(2026-10-16): `feat/130-reserved-limit-orders`에 적용. 전체 build/SpotBugs 성공, 테스트 313개 중 292개 통과·21개 건너뜀·실패 0개. 로컬 Valkey에서 실제 Pub/Sub/두 BE 동시 체결을 포함한 이벤트 테스트 5개 추가 실행, 모두 통과. 별도 읽기 검토에서 중요 결함 없음. DB 스키마 변경 없음. DB 테스트는 H2이며 실제 MySQL·배포 환경·거래소 장중 검증은 미실시. FE/AI 인계 내용은 `docs/reserved-limit-orders.md`에 기록했으며 외부 전송은 하지 않았다.

금요일 장 마감 후 생성한 지정가 주문이 주말 동안 예약 자산과 함께 PENDING으로 유지되고, 다음 거래일의 허용 시간에 새로 수신한 유효한 시세 이벤트가 조건을 만족하면 한 번만 체결된다. 개장했어도 새 이벤트가 없으면 대기한다. 사용자가 먼저 취소하면 체결되지 않는다. 시간 외 체결 및 전일 시세 체결은 발생하지 않는다.
