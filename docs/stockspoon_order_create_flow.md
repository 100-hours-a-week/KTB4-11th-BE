# 주문 생성 구현 흐름과 정책 결정 (v1)

이 문서는 `feat/13-order`의 주문 생성 HTTP API가 어떤 순서로 동작하는지와 구현 중 확정한 정책을 기록한다. 요청·응답의 간단한 계약은 [주문 생성 API](stockspoon_order_create.md), 앞서 만든 예약·취소 내부 규칙은 [주문 1단계](stockspoon_order_phase1.md)를 참고한다. 현재 주문은 **BE 내부 모의 주문**이며 키움에는 주문을 보내지 않는다.

원래 `03_주문_체결_정책_v1_확정본.md`의 실제 거래일·정규장 운영·개별 종목 거래정지 검사 조건은 이후 합의로 **현재 주문 생성 단계에서는 변경되었다.** 현행 접수 기준은 한국 시간 09:00 이상 15:30 미만이며 날짜·휴장일·실제 장운영 상태와 개별 종목 거래정지는 검사하지 않는다. 이는 실제 시장에서 거래 가능한 주문임을 보장하는 정책이 아니다. 향후 장 상태 판정 방식을 마련할 때 다시 검토한다.

AI 서버는 BE와 동일한 JWT 서명 시크릿을 사용하고 사용자 ID를 `sub`에 넣는다. 이 시크릿을 가진 AI 서버는 각 사용자에 대한 토큰을 발급할 수 있으므로 서버 내부에서만 보관해야 한다. 향후 v2의 일반 사용자 주문에서는 `actor`를 모든 요청의 필수 조건으로 둘 필요는 없지만, AI 주문과 사용자 주문의 출처를 구별할 수단은 유지해야 한다. 예를 들어 AI 토큰의 `actor: "AI"`는 유지하고 일반 사용자 토큰은 클레임 없이 `USER`로 처리할 수 있다. `order_source`는 요청 본문을 믿지 않고 BE가 결정한다.

## 한 건의 주문이 처리되는 순서

1. `POST /api/v1/accounts/{accountId}/orders`를 받는다. 기존 Spring Security가 access JWT 쿠키와 CSRF 토큰을 확인한다. 컨트롤러는 JWT의 `actor`가 `AI`인지 확인한다.
2. 요청 DTO에서 6자리 종목코드, 매수·매도, `limit` 주문, 양의 지정가·수량, 임시 `reason` 두 필드를 검사한다. 실패하면 주문 행을 저장하지 않는다.
3. JWT `sub`의 사용자 ID와 URL의 계좌 ID를 대조하고 계좌가 활성 AI 운용 계좌인지 확인한다. 타인 계좌는 403으로 거절해 키움 조회를 호출하지 않는다. 이어 **주문 생성 조건 검증**으로 한국 시간 09:00 이상 15:30 미만인지 확인하고, 키움 REST `ka10100` 종목정보의 종목코드·시장구분과 상품별 호가가격단위를 검사한다. 요일·휴일과 개별 종목 거래정지 여부는 검사하지 않는다.
4. DB 트랜잭션에서 계좌 행을 `PESSIMISTIC_WRITE`로 조회한다. 소유자·활성 상태를 다시 검사한 뒤 매수는 주문 가능 현금, 매도는 매도 가능 수량을 계산한다. 잠금은 같은 계좌의 동시 예약·취소가 서로의 계산을 앞지르지 않게 하기 위한 것이며 트랜잭션 종료 시 해제된다. 이 규칙은 같은 계좌를 변경하는 후속 기능도 동일한 잠금 순서에 참여해야 성립한다.
5. 검사에 통과하면 `trade_orders`에 `order_source=AI`, `status=PENDING`, 지정가·수량·AI 근거를 저장한다. 매수 `reserved_cash`는 지정가 × 수량, 매도는 0이다. 아직 `cash_balance`나 `holdings`를 변경하지 않는다.
6. HTTP 201로 주문 ID, 상태 `pending`, 해당 주문의 `reserved_cash`, 생성 시각, 빈 `executions`를 반환한다. 체결은 이후 별도 기능이다.

예를 들어 `cash_balance=1,000,000원`, 기존 pending 매수 예약금 합계가 `300,000원`이면 `available_cash=700,000원`이다. 70,000원에 2주를 매수하는 주문은 140,000원을 새로 예약하므로 접수 후 `available_cash=560,000원`이다. 현금 잔액은 체결 전까지 1,000,000원 그대로다. 매도는 `sellable_quantity=보유수량−pending 매도 주문 수량 합계`로 검사한다. 현재 계좌 조회 응답에는 `available_cash`가 아직 노출되지 않고 주문 내부 계산에만 쓰인다.

### 1단계 설명: 인증과 계좌 권한 확인

**목적:** 주문을 보낸 주체가 v1에서 허용한 AI인지, URL의 계좌가 토큰에 적힌 사용자 소유인지 확인한다. `user_id`를 별도 요청 헤더나 본문에서 받아 신뢰하지 않는다.

**실제 흐름:** `SecurityConfig`는 `Cookie: access_token=...`에서 JWT를 읽는다. `JwtConfig`의 access decoder가 HS256 서명, 발급자, 만료 시각 및 `type=access`를 검증한다. POST 요청에는 기존 CSRF 검사도 적용된다. 인증을 통과한 뒤 `OrderController`가 `actor=AI`를 요구한다. 이어 요청 필드의 기본 검사를 거쳐 JWT의 `sub`를 사용자 ID로 읽고, `OrderService.assertOrderableAccount`가 URL의 `accountId`와 사용자 ID에 일치하는 활성 계좌를 조회한다. 그 계좌가 AI 운용 계좌인지도 확인한다. 키움 시장데이터를 조회하기 전에 이 권한 검사를 마친다. 주문 저장 트랜잭션에서는 잠근 계좌의 소유자를 다시 확인한다.

예를 들어 계좌 11이 사용자 1의 소유라면 `sub=1`, `actor=AI`인 유효한 토큰으로 접근할 수 있다. `sub=2`라면 `403 FORBIDDEN_ACCOUNT`, 일반 사용자 로그인 토큰처럼 `actor`가 없다면 `403 AI_ORDER_ONLY`로 거절한다. 토큰이 없거나 검증에 실패하면 인증 단계에서 거절된다. CSRF 확인값이 유효하지 않으면 주문 컨트롤러까지 진행하지 않는다.

**결정 근거:** v1은 AI가 사용자 계좌를 대신 운용하고 일반 사용자는 직접 주문하지 않는다는 합의에 따라 `actor=AI`를 요구한다. 계좌 ID만 알면 타인 계좌에 주문할 수 있어서는 안 되므로, JWT `sub`와 DB에 저장된 계좌 소유자를 비교한다. 요청 본문의 `order_source`나 임의의 `user_id`로 출처와 권한을 결정하지 않는다.

**코드·검증 근거:** `config/SecurityConfig.java`의 쿠키 토큰 추출·CSRF 설정, `config/JwtConfig.java`의 access decoder, `order/OrderController.java`의 `actor`·`sub` 검사, `order/OrderService.java`의 `assertOrderableAccount`와 예약 시 소유자 재검사, `order/OrderControllerTests.java`의 일반 사용자 토큰·타인 계좌 거절 테스트를 참고한다.

**남는 전제:** AI 서버는 BE와 같은 JWT 서명 비밀키를 보유하므로 임의 사용자 ID를 `sub`로 한 토큰을 만들 수 있다. 현재 소유자 검사는 **토큰에 적힌 사용자와 계좌가 일치하는지** 확인하며, AI가 어떤 사용자 ID를 선택했는지 별도로 승인하지 않는다. 공유 비밀키는 AI 서버 내부에서만 보관해야 한다.

### 2단계 설명: 주문 요청값 검증

**목적:** 키움 시장 조회와 DB 주문 예약 전에, 주문의 형식과 이번 v1에서 지원하는 범위를 확인한다. 형식이 틀린 요청은 계좌 잔액을 계산하거나 주문을 저장하지 않는다.

**실제 흐름:** `OrderController`의 `@Valid @RequestBody`가 JSON을 `OrderCreateRequest`로 변환하고 DTO 제약을 검사한다. `stock_code`는 숫자 6자리, `order_side`와 `order_type`은 빈 값이 아니어야 하며, `quantity`는 1 이상의 정수다. `reason` 객체가 있으면 그 안의 `decision_id`와 `summary`는 비어 있지 않아야 하고 각각 100자·500자를 넘을 수 없다. 이어 컨트롤러는 `order_type=limit`만 허용하고, `order_side`를 매수 `buy` 또는 매도 `sell`로 해석하며, `limit_price`가 양수인지 확인한다. v1 AI 주문에서는 `reason` 객체 자체도 필수로 검사한다. `OrderService.reserveLimit`에서도 종목코드·수량·가격과 근거 길이를 재확인하고, 주문금액 계산 시 정수 범위를 넘으면 거절한다. 호가가격단위 검사는 이 단계가 아닌 다음 시장 검증에서 수행한다.

예를 들어 `order_type=market`은 아직 지원하지 않아 거절된다. `reason=null`은 DTO 구조상 표현할 수 있지만 v1 AI 주문 컨트롤러에서 거절된다. `limit_price=70000`, `quantity=2`인 지정가 매수의 주문금액은 뒤의 예약 단계에서 140,000원으로 계산된다. 단순 입력 오류로 던진 `OrderException`은 `400 INVALID_ORDER`를 반환하며, DTO의 Bean Validation 오류는 Spring MVC의 요청 검증 단계에서 처리된다.

**결정 근거:** 사용자와 합의한 v1 범위는 지정가 주문 접수까지이며 시장가는 체결 기능과 함께 구현한다. AI 판단 근거의 최종 형식은 미정이므로 `decision_id`·`summary` 두 필드만 임시로 받는다. 향후 사용자 주문은 근거 생략·`null`을 허용할 계획이지만 지금은 AI 주문만 열려 있어 필수로 검사한다. 수량은 주 단위 정수로 다루며, 잘못된 값으로 현금·보유수량 예약이 계산되지 않도록 한다.

**코드·검증 근거:** `order/OrderCreateRequest.java`의 JSON 필드 매핑·Bean Validation, `order/OrderController.java`의 지원 주문 방식·매수/매도·지정가·근거 검사, `order/OrderService.java`의 내부 입력 재검사와 주문금액 범위 검사, `order/OrderControllerTests.java`의 시장가·근거 누락 거절 테스트를 참고한다.

**남는 전제:** `reason`의 두 필드는 임시 계약이다. AI 팀과 최종 근거 형식을 정하면 요청 DTO, 저장 방식, 응답 계약을 함께 조정해야 한다. 현재 `decision_id`는 중복 요청 차단 키가 아니므로 같은 내용을 두 번 보내면 별도 주문 두 건이 만들어진다.

### 3단계 설명: 주문 생성 시간·종목·호가단위 검증

**목적:** 형식이 올바른 주문이라도 정해진 생성 시간 밖이거나 v1 대상 밖의 상품·잘못된 호가단위 가격이면 예약하지 않는다. 키움은 여기서 종목정보의 출처이며, 키움에 실제 주문을 전송하지 않는다.

**실제 흐름:** `OrderController`가 계좌 권한을 먼저 확인한 다음 `OrderMarketValidator.validateLimit`을 호출한다. 검증기는 서버 현재 시각을 `Asia/Seoul`로 변환해 09:00:00 이상 15:30:00 미만인지 확인한다. 요일·휴일은 검사하지 않으며 키움 웹소켓 `0s`의 장운영구분도 사용하지 않는다. 시간 밖이면 `409 ORDER_WINDOW_CLOSED`를 반환하고 종목 조회는 하지 않는다. 이어 키움 REST `ka10100`으로 요청 종목을 조회해 `return_code=0`, 요청·응답 종목코드 일치, `marketCode` 존재를 확인한다. 조회 실패나 불완전한 응답은 `503 MARKET_DATA_UNAVAILABLE`이다. `marketCode`가 현재 허용 집합 `0/8`에 없거나 지정가가 해당 상품의 호가가격단위에 맞지 않으면 `400 INVALID_ORDER`로 거절한다. 세 검사를 통과해야 DB 예약으로 진행한다.

예를 들어 일반 주식의 지정가가 70,000원이면 이 가격대의 100원 단위에 맞는다. 70,050원은 맞지 않아 거절된다. ETF의 2,005원은 5원 단위에 맞고 2,001원은 맞지 않는다. `ka10100`의 `state`와 `orderWarning`은 개별 종목의 거래정지 판정에 사용하지 않는다.

**결정 근거:** 사용자는 v1에서 날짜 제한 없이 한국 시간 09:00~15:30에 주문 생성을 허용하고, 이후 허용 시장코드를 `0/8`로 좁혀 ETN을 제외했으며, 개별 종목 거래정지는 검사하지 않기로 정했다. 기존 `0s` 방식은 장중 재연결 직후 시작 이벤트를 받지 못하면 실제 장중에도 접수를 거절할 수 있어 시간 규칙으로 교체했다. 종목의 시장구분은 키움 `ka10100`, 호가가격단위는 거래소 규칙을 근거로 한다.

**코드·자료·검증 근거:** `order/OrderMarketValidator.java`의 한국 시간 판정·호가단위 검사와 `market/kiwoom/KiwoomMarketClient.java`의 `stockInfo`를 참고한다. `order/OrderMarketValidatorTests.java`는 고정된 테스트 시계로 09:00·15:30 경계와 주말을 확인한다. 실제 서버는 현재 시각을 읽는다. 외부 자료는 [키움 REST API 가이드](https://openapi.kiwoom.com/guide/apiguide)의 종목정보조회(`ka10100`)와 [한국거래소 호가가격단위](https://regulation.krx.co.kr/contents/RGL/03/03010100/RGL03010100T3.jsp)다. 시간 범위는 외부 API가 아닌 서비스 정책이다.

**남는 전제:** 시간 규칙은 실제 장 개장을 검증하지 않는다. 주말·휴일, 임시 개장 지연·조기 마감에도 시각만 맞으면 이후 종목정보·호가단위 검증으로 진행한다. 허용 시장코드만으로 실제 개별 종목의 거래 가능 여부를 보장하지도 않는다. 주문 가능 시간 검사는 DB 예약 트랜잭션 전에 한 번 수행하므로 경계 시각 직전에 통과한 주문이 15:30 이후 저장될 가능성도 있다.

### 4단계 설명: 계좌 잠금과 주문 가능 자산 검사

**목적:** 같은 계좌의 동시 주문이 같은 현금이나 보유 주식을 중복 예약하지 않게 하고, 실제 저장 직전 계좌 소유자와 상태를 다시 확인한다.

**실제 흐름:** `OrderService.reserveLimit`의 DB 트랜잭션에서 `AccountRepository.findLockedById`가 `PESSIMISTIC_WRITE`로 계좌 행을 읽는다. 잠근 계좌의 소유자·활성 상태·AI 운용 여부를 재확인한다. 매수 주문은 `cash_balance − pending 주문의 reserved_cash 합계`로 주문 가능 현금을 계산하고, `지정가 × 수량`이 그보다 크면 거절한다. 곱셈이 `long` 범위를 넘을 때도 거절한다. 매도 주문은 해당 종목의 `보유 수량 − pending 매도 주문 수량 합계`와 요청 수량을 비교한다. 부족하면 주문을 저장하지 않는다.

예를 들어 현금 잔액 100만 원에 기존 매수 예약금이 30만 원이면 주문 가능 현금은 70만 원이다. 7만 원에 2주를 매수하면 14만 원을 추가 예약할 수 있다. 반대로 10주 보유 중 7주 매도 주문이 대기 중이라면 새로 매도 가능한 수량은 3주다.

**결정 근거:** 주문 접수와 모의체결을 분리하므로 접수 시 현금·보유 수량을 실제로 차감하지 않는다. 대신 대기 주문의 예약금을 현금 계산에서, 대기 매도 수량을 보유 수량 계산에서 빼서 중복 사용을 막는다. 계좌 행 잠금은 같은 계좌를 대상으로 이 잠금 규칙에 참여하는 트랜잭션들이 예약 계산을 순서대로 수행하도록 하기 위한 선택이다.

**코드·검증 근거:** `account/repository/AccountRepository.java`의 `findLockedById`, `order/OrderService.java`의 `reserveLimit`·`availableCash`·`sellableQuantity`, `order/OrderRepository.java`의 pending 예약 합계 조회, `order/OrderServiceTests.java`의 매수·매도 예약과 부족액 거절 테스트를 참고한다.

**남는 전제:** 같은 계좌의 자산을 바꾸는 다른 기능도 동일한 잠금 순서를 따라야 동시성 제어가 성립한다. 주문 생성 시간·종목 검증은 이 DB 트랜잭션 전에 수행되므로 시간 경계와 DB 저장을 하나의 원자적 판단으로 묶지는 못한다.

### 5단계 설명: 대기 주문 저장

**목적:** 검증된 주문의 조건과 AI 판단 근거를 체결 대기 상태로 보존하고, 이후 주문에서 사용할 예약 금액·수량을 남긴다.

**실제 흐름:** `OrderService`가 `Order.pendingLimit`을 만들고 `trade_orders`에 저장한다. 계좌, 종목코드, 매수·매도, `order_type=LIMIT`, 지정가, 수량, `order_source=AI`, `status=PENDING`, 생성 시각과 임시 판단 근거 `decision_id`·`decision_summary`를 기록한다. 매수의 `reserved_cash`는 지정가 × 수량, 매도는 0원이다. 이 시점에는 `cash_balance`와 `holdings`를 변경하지 않는다.

예를 들어 7만 원에 2주를 매수하는 주문은 예약금 14만 원의 `PENDING` 주문 한 건으로 저장된다. 이후 주문 가능 현금 계산에 이 14만 원이 반영된다. 같은 요청을 다시 보내고 모든 검사를 통과하면 별도 주문 한 건이 더 생긴다.

**결정 근거:** BE 자체 모의체결은 후속 기능이다. 지금의 `PENDING`은 접수·대기 중이라는 뜻이며 체결 완료를 의미하지 않는다. AI 주문의 `order_source`는 요청 본문을 믿지 않고 BE가 정한다. `reason`의 두 필드만 저장하는 방식은 AI 판단 근거 형식 확정 전의 임시 계약이다.

**코드·검증 근거:** `order/OrderService.java`의 `orders.save`, `order/Order.java`의 `pendingLimit`과 필드 매핑, `order/OrderControllerTests.java`의 AI 출처·근거·동일 요청 2건 저장 테스트, `order/OrderServiceTests.java`의 잔액·보유 수량 불변 테스트를 참고한다.

**남는 전제:** `EXECUTED` 상태는 모델에 정의돼 있지만 현재 체결 엔진은 없다. 체결 때 현금·보유 주식·예약금을 한 트랜잭션에서 어떻게 갱신할지는 후속 구현 범위다.

### 6단계 설명: HTTP 응답

**목적:** AI 서버에 주문이 접수됐다는 결과와 이후 추적에 필요한 주문 ID·상태를 알려준다. 응답은 체결 성공 통지가 아니다.

**실제 흐름:** `OrderController`는 저장된 `Order`를 `OrderCreateResponse.from`으로 변환하고 HTTP `201 Created`로 반환한다. JSON에는 `message=success`, 주문·계좌 ID, 종목코드, 매수·매도, 주문 방식, 지정가·수량, `order_status=pending`, 해당 주문의 `reserved_cash`, UTC 생성 시각, 빈 `executions=[]`가 들어간다. `order_source`와 AI 근거는 현재 생성 응답에 포함되지 않고 주문 행에 저장된다. 실패하면 `OrderExceptionHandler`가 `code`·`message`를 반환하며, 인증·CSRF·DTO 단계의 오류는 각각 해당 프레임워크 처리 경로를 따른다.

예를 들어 7만 원에 2주 매수 주문이 접수되면 `reserved_cash=140000`, `order_status=pending`, `executions=[]`가 반환된다. 이는 2주를 샀다는 뜻이 아니라 14만 원을 해당 주문에 예약했다는 뜻이다.

**결정 근거:** 신규 주문을 만들었으므로 `201`을 사용하고, 접수와 체결을 분리하므로 상태를 `pending`으로 돌려준다. 빈 체결 배열은 아직 체결 내역이 없다는 현재 상태를 명시한다.

**코드·검증 근거:** `order/OrderController.java`의 `@ResponseStatus(CREATED)`와 응답 반환, `order/OrderCreateResponse.java`의 필드 매핑, `order/OrderExceptionHandler.java`의 주문 오류 응답, `order/OrderControllerTests.java`의 `201`·`pending`·예약금 확인을 참고한다. 응답 예시는 [주문 생성 API](stockspoon_order_create.md)에 있다.

**남는 전제:** 생성 응답의 `executions`는 현재 항상 빈 배열이다. 체결 엔진과 주문 내역 조회 API가 아직 없으므로 AI 근거와 체결 결과를 조회·표시하는 계약은 후속 작업에서 확정해야 한다.

## 주문 생성 이후: 대기 주문 취소의 현재 범위

주문 생성 API가 반환한 `pending` 주문은 체결 엔진이 없는 현재 상태에서 자동으로 체결되지 않는다. `OrderService.cancel(accountId, orderId)`라는 **BE 내부 취소 로직은 구현돼 있다.** 이 로직은 계좌 행을 잠그고 해당 계좌의 주문을 조회해 `PENDING`일 때만 `CANCELLED`로 바꾼다. 취소 시 `reserved_cash`를 0으로 만들고 `cancelled_at`을 기록한다. 매수 주문은 주문 가능 현금 계산에서 예약금이 빠지고, 매도 주문은 pending 매도 수량 합계에서 제외돼 예약 수량이 풀린다. 현금 잔액이나 보유 수량을 되돌리는 동작은 필요하지 않다. 접수 시 실제 잔액·보유 수량을 변경하지 않았기 때문이다.

**현재 `OrderService.cancel`을 호출하는 취소 HTTP API는 없다.** 따라서 FE나 AI 서버가 HTTP 요청으로 주문을 취소할 수 없다. 주문 내역 조회 HTTP API와 모의체결 엔진도 아직 없다. 취소 API를 만들 때는 지금 내부 메서드에 없는 요청자 인증·계좌 소유권 검사를 연결해야 한다. 현재의 내부 취소 규칙과 예약 해제는 `order/OrderService.java`, `order/Order.java`, `order/OrderServiceTests.java`에서 확인할 수 있다.

## 주문 생성 시간과 종목·가격을 확인하는 과정

### 1. 한국 시간으로 확인하는 주문 생성 시간

`OrderMarketValidator`는 실제 서버 시계를 `Asia/Seoul`로 변환해 09:00:00 이상, 15:30:00 미만일 때만 주문 생성의 다음 검사로 진행한다. 08:59:59와 15:30:00에는 `ORDER_WINDOW_CLOSED`(409)를 반환한다. **요일·휴일은 검사하지 않는다.** 예를 들어 일요일 10:00에도 시각 조건은 통과한다. 이 시각은 실제 장 운영 상태를 뜻하지 않는다.

기존 구현은 키움 웹소켓 `0s`의 장시작 이벤트를 현재 연결에서 받아야 주문을 허용했다. 장중에 웹소켓을 새로 연결하면 시작 이벤트가 즉시 오지 않을 수 있어 사용자 주문이 거절될 수 있었고, 반대로 종료 이벤트가 누락될 수도 있었다. 이번 정책 변경으로 주문 판단에서 `0s` 구독·상태 보관을 제거했다. 현재가 `0B`와 호가 `0D` 구독은 유지하며, 종목 시세 구독 연결 상태는 주문 생성 시간의 조건이 아니다.

### 2. 종목과 허용 시장 확인

시간 확인 다음에 주문 종목코드로 키움 REST 종목정보 조회 `ka10100`을 호출한다. 키움에 주문을 보내는 호출이 아니다. `return_code=0`, 응답의 `code`와 요청 종목코드 일치, `marketCode`의 존재를 검사한다. 요청 실패·거부·응답 형식 오류는 `MARKET_DATA_UNAVAILABLE`(503)로 거절한다.

현재 허용하는 `marketCode`는 `0`(코스피)과 `8`(국내 ETF)이다. ETN 코드 `60/70/90`은 거절한다. `state`의 공식 명칭은 ‘종목상태’이지만 키움의 응답 예시와 실제 조회에서는 `증거금20%|담보대출|신용가능`처럼 증거금·담보·신용 정보를 담았다. `orderWarning`은 투자유의 분류다. **v1 주문 접수는 두 필드로 개별 종목의 거래정지 상태를 판정하지 않는다.** 따라서 허용 시장의 종목이고 다른 주문 조건을 만족하면 실제 거래정지 종목도 모의 주문에 접수될 수 있다. 삼성전자 `005930`의 시장코드 `0`, KODEX 200 `069500`의 시장코드 `8`은 실서버 조회로 확인했다. 우선주의 시장구분 응답은 확인이 남아 있다.

### 3. 지정가의 호가가격단위

종목 구분에 따라 지정가가 KRX 호가단위의 배수인지 확인한다. 일반 주식은 가격대별 1·5·10·50·100·500·1,000원 단위를, ETF는 2,000원 미만 1원 / 이상 5원 단위를 적용한다. 예를 들어 70,050원은 일반 주식의 해당 가격대 호가단위인 100원에 맞지 않아 거절한다. 이 단계는 가격 형식 검사이며 체결 가능 가격이나 시세의 최신성을 보장하지 않는다.

## 검증과 남은 작업

자동 테스트는 AI JWT와 일반 사용자 JWT 구분, 타인 계좌 차단, 지정가 생성과 근거 저장, 같은 요청 두 번의 별도 주문, 주문 가능 시간 경계·시장구분·호가단위 거절, 웹소켓 연결 종료 시 시세 상태 폐기 등을 확인한다. 삼성전자·KODEX 200 종목정보 조회와 현재가·호가 WebSocket 등록은 별도로 실서버에서 확인했다. 시간 판정은 키움 실시간 장 상태를 사용하지 않으며, 종단간 HTTP 주문 성공의 라이브 검증은 아직 하지 않았다.

체결 엔진에서는 대기 주문 종목의 동적 현재가 구독, 시세 최신성 확인, 체결·현금·보유종목의 한 트랜잭션 갱신이 필요하다. 시장가 주문, 주문 취소 HTTP API, 계좌 조회의 `available_cash` 제공, v2 사용자 주문도 후속 범위다.

## 이슈: 주문 생성 가능 환경 검증

**배경:** 계좌에 현금이 충분해도 주문 생성 시간·대상 상품·호가가격단위가 맞지 않으면 지정가 주문을 받아서는 안 된다. 키움 시세 구독 성공 자체는 정규장 운영을 뜻하지 않는다. 개별 종목 거래정지 여부는 v1 주문 접수 정책에서 제외했다.

**현재 처리:** 주문 API는 위의 시간·종목·가격 검증 1~3단계를 거쳐야만 DB 주문 예약으로 진행한다. 한국 시간 09:00 이상 15:30 미만인지 확인한 뒤 키움 REST `ka10100`의 정상 응답·종목코드·허용 시장구분과 지정가 호가단위를 검사한다. `state`·`orderWarning`은 접수 판정에 사용하지 않는다. 시간 밖이면 409, 종목 정보를 확인할 수 없으면 503으로 거절하고 주문 행은 남기지 않는다. 날짜·휴장일·실제 장운영 상태는 검사하지 않으며 키움에 실제 주문을 보내지 않는다.

**확인이 남은 지점:**

- [ ] 추후 휴장일·임시 개장 지연·조기 마감을 반영할 신뢰 가능한 장 상태 판정 방법을 검토한다. 현재는 시간만 맞으면 실제 휴장 중에도 모의 주문을 접수할 수 있다.
- [ ] 우선주의 `ka10100` 시장구분 응답을 확인한다. 개별 종목 거래정지 판정은 이번 정책에서 제외하며 별도 검증 작업으로 추적하지 않는다.
- [ ] 주문 가능 시간 확인과 DB 주문 저장 사이에 15:30 경계를 지나는 경우를 검토한다. 시간 확인은 계좌 잠금 트랜잭션 전에 수행된다.

**검증 기준:** 09:00 전·15:30 이후·종목정보 실패·허용 범위 밖 상품·호가단위 오류는 각각 주문 없이 거절되고, 허용 시각의 대상 종목 지정가 주문은 `pending`으로 저장되어야 한다. 날짜·휴일·개별 종목 거래정지 여부는 결과를 바꾸지 않는다. 자동 테스트와 실서버 검증 결과를 구분해 기록한다.

종목·가격 근거: [키움 REST API 가이드](https://openapi.kiwoom.com/guide/apiguide)의 **국내주식 → 종목정보 → 종목정보조회(ka10100)**, [한국거래소 주식 호가가격단위](https://regulation.krx.co.kr/contents/RGL/03/03010100/RGL03010100T3.jsp), [한국거래소 ETF 호가가격단위](https://regulation.krx.co.kr/contents/RGL/03/03060101/RGL03060101.jsp). 09:00~15:30은 실제 장 상태 조회값이 아닌 서비스의 임시 주문 정책이다.
