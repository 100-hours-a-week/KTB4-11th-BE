# Redis 전환 배포·운영 인계

## 현재 상태와 인프라 요청

2026-10-12 사용자 확인: 배포 Valkey·MySQL·BE 실행 환경 접속 설정은 아직 없다. 구현 및 로컬 전체 회귀는 282개 중 276개 통과, 실제 키움 연결 6개 건너뜀, 실패·오류 0건이다. 배포용 `bootJar` 빌드는 성공했다. 실제 배포·배포 환경 검증은 수행하지 않았다.

인프라 팀에 다음을 전달한다. 이 문서는 전달용 초안이며 팀원에게 메시지를 발송한 기록은 아니다.

- Valkey 키는 기존 `quote:*`, `session:*`, `token:*` 외에 승인된 **`coord:*`를 추가**한다. 채널은 `quotes:*`이며 개별 `SUBSCRIBE`를 사용한다. `PSUBSCRIBE`를 사용하지 않는다.
- Lua, ZSET, Redis 시간 조회와 연결 초기화 명령이 필요하다. 상세 ACL과 로컬 검증 결과는 [권한 요구 사항](valkey-acl-requirements.md)을 따른다. `{accepting}` 해시 태그를 변경하지 않는다.
- 담당 BE 한 대와 일반 BE 여러 대는 같은 DB·Valkey를 사용한다. 담당만 키움 REST·WebSocket과 토큰을 사용한다. 자동 담당 인계는 없다.
- Valkey 주소·포트·TLS·인증 방식, MySQL 연결 설정, 담당 BE 내부 주소·통신 경로, 실행 환경 및 이전 정상 이미지 식별자를 제공한다. IAM 인증은 현재 구현으로 지원 완료된 상태가 아니다.
- `/internal/**`는 내부 BE 간 통신용이며 외부 접근을 제한한다. 모든 BE에 같은 전용 비밀키를 주입하고 `X-Kiwoom-Collector-Key` 헤더로 인증한다.

## 설정 파일 예시

[공통 환경변수](deployment-common.env.example)와 [담당 BE](deployment-collector.env.example) 또는 [일반 BE](deployment-consumer.env.example)의 값을 각각 인프라의 환경변수/비밀 관리 도구로 합쳐 주입한다. 앱이 이 예시 파일들을 자동으로 읽는 것은 아니다. 로컬 `.env.local`을 쓸 때도 실제 값으로 합친 별도 파일을 사용하며 Git에서 제외한다.

모든 `REPLACE_WITH_*`와 빈 필수 비밀값을 실제 설정으로 교체한다. TLS와 포트는 예시를 그대로 확정하지 않고 배포 환경을 확인한다. 일반 BE에 키움 앱 키·앱 비밀값을 주입하지 않는다. `JPA_DDL_AUTO=validate`는 스키마 검증 예시이며 실제 기존 스키마와 호환되는지 먼저 확인한다. 데이터베이스를 자동 생성·삭제하는 설정을 배포에 사용하지 않는다.

현재 `.github/workflows/cd.yaml`은 main CI 성공 후 EC2의 `/opt/cloud`에서 인프라 저장소를 갱신하고 `scripts/deploy.sh image backend <이미지 태그>`를 실행한다. 이 작업 공간에는 해당 인프라 Compose·스크립트가 없다. 인프라 저장소에서 역할별 서비스와 위 환경변수 주입을 구성해야 한다. BE 코드의 기본 담당·시세 플래그는 `false`이므로 새 이미지 배포만으로 Redis 수집 구조가 활성화되지는 않는다.

## 실제 환경 검증 순서

1. 접속 정보와 역할별 설정을 확보하고, 운영 주문이 발생하지 않는 검증 환경을 지정한다. 실제 검증용 계좌·종목·데이터 처리 범위와 부하 규모는 실행 전에 정한다.
2. 실제 BE의 Spring/Lettuce로 배포 Valkey 인증·TLS·키 범위·명령·TTL·Lua·개별 채널 Pub/Sub를 확인한다. 로컬 ACL 테스트는 임시 ACL 사용자를 생성하므로 관리 권한이 없는 배포 저장소에 그대로 실행하지 않는다.
3. 담당 BE 1대와 일반 BE 2대를 실제 MySQL·Valkey에 연결한다. 담당의 활동 키와 키움 로그인·구독 성공, 일반 BE의 내부 REST 인증과 공유 종목정보 조회를 확인한다. 잘못된 내부 비밀키로 조회하면 거절되어야 한다.
4. 실제 현재가·호가의 Redis 저장과 두 일반 BE의 수신을 확인한다. 검증 주문의 주문별 체결·현금·보유 수량을 대조한다. 실제 키움 토큰·시세 검증은 장중에 수행한다. 외부 키움 호출 한도를 넘기는 부하를 보내지 않는다.
5. 담당 종료·Redis 연결 장애·담당 재시작을 검증한다. 신규 주문·체결 중단, 대기 주문 유지, DB 상태 조회·취소 가능 여부와 이전 연결 시세 거절을 확인한다.
6. 승인된 검증 범위에서 단계적으로 부하를 늘려 응답 지연·실패 유형·알림 처리 지연·DB 잠금·CPU/메모리를 기록한다. 시세 부하는 가짜 발행 경로 또는 별도 시험 환경을 사용한다. 로컬 처리 수치로 운영 용량을 확정하지 않는다.

계좌·종목·실행 환경·측정 규모가 아직 없으므로 위 절차를 실제로 실행했다고 표시하지 않는다. 실제 접속 정보를 받은 뒤 배포 환경용 검증 방법을 구체화한다. 기존 자동 다중 BE 테스트는 localhost Valkey와 테스트 H2를 사용하므로 실제 MySQL 검증을 대신하지 않는다.

## 최초 전환과 담당 재배포

최초 전환은 주문 유입을 통제하는 배포 시간에 진행한다. 기존 메모리 수집 BE와 새 담당이 같은 토큰으로 동시에 키움에 연결하지 않도록 기존 BE의 수집 프로세스를 종료한 뒤 새 담당을 시작한다. 새 담당의 활동·키움 로그인·구독·첫 시세를 확인하고 일반 BE를 시작한 뒤 주문 처리를 재개한다. DB의 대기 주문은 새 구성에서 복구하며 수신 전의 이전 가격으로 체결하지 않는다.

담당 재배포는 기존 담당 종료 후 새 담당 시작 순서다. 새 담당을 먼저 띄우는 일반적인 중첩 배포는 활동 키 때문에 시작에 실패할 수 있다. 정상 종료하면 소유한 활동 키를 정리한다. 강제 종료나 Redis 장애로 정리하지 못하면 15초 TTL 만료를 기다린다. 활동 키를 임의 삭제해 살아 있는 담당과 경쟁시키지 않는다. 그동안 신규 주문·체결은 중단될 수 있다.

일반 BE 증설에는 담당 플래그를 부여하지 않는다. 일반 BE 재시작 후 DB 대기 주문의 종목별 채널을 다시 구독하고 최신 캐시로 판단한다. Pub/Sub는 연결이 끊긴 동안의 알림을 재생하지 않는다.

## 장애 대응과 복구

| 상황 | 기대 동작과 대응 |
|---|---|
| 담당 중단 | 신규 조회·주문·체결 중단, DB 대기 주문 유지. 기존 담당 종료·활동 TTL 정리를 확인하고 담당 한 대를 재시작한다. |
| Redis 연결 장애 | 시세 출처 검증 불가로 신규 주문·체결 중단. 네트워크/TLS/인증/ACL을 복구한다. 자격을 잃은 담당은 Redis 복구만으로 재획득하지 않으므로 재시작한다. |
| 내부 요청 거절 | 역할 플래그·담당 URL·전용 비밀키 주입을 확인한다. 비밀키를 로그에 출력하지 않는다. 일반 BE가 직접 키움에 연결하도록 바꾸지 않는다. |
| REST 대기 초과 | 동일 TR 호출 순서 대기 3초 초과 시 외부 호출 전 실패, 내부 API 503. 전체 HTTP 응답 제한과 별개이며 자동 재시도하지 않는다. |
| 새 담당의 시세 미수신 | 새 연결의 로그인·종목 등록·활동 상태를 확인하고 첫 시세를 기다린다. 저장 TTL 1일을 신선도 보장으로 사용하지 않는다. |
| 주문 처리 지연 | 알림 처리 대기·DB 잠금·REST 평가 조회와 자원 사용량을 확인한다. TTL·현재가 사용 기준·대기 상한은 임의 변경하지 않는다. |

프로세스 기동 또는 일반 HTTP 응답만으로 담당 소유권·키움 구독·시세 유효성이 정상이라고 판단하지 않는다. 현재 전용 운영 준비 상태 API가 있다고 가정하지 말고 위 동작과 키·로그를 함께 확인한다.

## 롤백

기존 수집 담당을 종료하고 이전 정상 이미지와 그 이미지에 맞는 설정으로 복구한다. 메모리 수집 방식의 이전 이미지로 되돌릴 경우 BE 여러 대를 동시에 수집하도록 실행하지 않고 V1처럼 한 대에서 먼저 복구한다. DB의 이미 체결된 주문·현금 변경은 이미지 롤백으로 되돌리지 않는다. 대기 주문 상태와 새로 수신한 시세를 확인한 후 처리를 재개한다. 공유 Valkey 전체 삭제나 유효 토큰 삭제를 롤백 절차로 사용하지 않는다.
