# Redis/Valkey 전환 설계 초안

작성일: 2026-10-11
현재 상태(2026-10-12): 주요 Redis 전환 구현, 로컬 다중 BE·장애/복구·ACL 검증 및 실제 키움 연결 검증을 마쳤다. 배포 연결 설정은 미준비이며 실제 배포 검증과 부하 측정이 남아 있다. 아래 단계별 기록은 작성 당시 결과이며 최신 진행 상태는 [redis-deployment-checklist.md](redis-deployment-checklist.md)를 참고한다.

## 목적과 범위

동일한 BE 여러 대가 최신 시세와 REST 조회 결과를 공유한다. 설정으로 지정한 BE 한 대만 키움 WebSocket 연결과 REST 호출을 수행한다. 담당 장애 시 자동 인계하지 않으며 담당을 재시작해 복구한다.

기존 현황은 [in-memory-data-and-redis-plan.md](in-memory-data-and-redis-plan.md)를 참고한다. 이번 범위는 기존 캐시 이전뿐 아니라 종목정보 REST 결과 캐싱도 포함한다. 계좌 잔고·주문·Refresh Token 해시 등 DB 데이터와 요청 내부 임시 계산값은 기존 구조를 유지한다.

## 잠정안과 인프라 요구사항

- 일반 BE에서 담당 BE로 REST 조회 요청을 보내는 방식은 내부 HTTP가 잠정안이다. 사용자가 추후 변경 가능함을 명시했다.
- 저장 키는 `quote:*`, `token:*`, 협의한 `coord:*`를 사용한다. `session:*`는 현재 로그인 구조 전환에 사용하지 않는다.
- Pub/Sub 채널은 `quotes:*`다. 저장 키 권한과 채널 권한은 따로 확인한다.
- 추가 접두사 및 사용하는 명령, TLS·인증·엔진 버전·Serverless 제한을 인프라 팀에 전달한다. 접두사 허용만으로 모든 명령이 허용됐다고 가정하지 않는다.
- 로컬 개발은 배포 Valkey 환경과 호환되는 버전·ACL·명령 제약을 맞춘다.
- 초기에는 220ms 간격을 TR별로 적용했다. 이후 사용자 제공 공식 FAQ의 실전 TR당·토큰별 5회 기준으로 최근 1초 최대 5회까지 즉시 전송하고 초과 요청만 대기하도록 변경했다. 담당은 단일 계좌/토큰을 운용하며 모의투자 한도는 별도 정책이다.

## 구현 계획을 구체화할 순서

1. **기존 시세·체결 검증 조사:** OrderExecutionService, OrderExecutionListener, Controller의 연결·시각·DB 잠금을 검토하고 다중 BE 동작을 정의한다.
2. **키·JSON 계약 작성:** 현재가·호가·종목정보·토큰·코스피·coord 데이터의 이름, 버전, 시각, 출처, TTL을 정의한다. 가격은 정밀도를 유지한다.
3. **로컬 Valkey와 연결 설정:** 주소·인증·TLS와 담당 설정을 분리하고 개발 실행 방법을 문서화한다.
4. **공유 캐시 구현 계획:** Redis 읽기·쓰기, TTL, 동일 요청 합치기, REST 응답의 최신 WebSocket 값 덮어쓰기 방지를 명세한다.
5. **담당 통신 계획:** 잠정 내부 HTTP의 접근 보호·요청 제한·오류·재시도와 전체 구독 수요 집계를 정의한다. 다른 BE는 키움을 직접 호출하지 않는다.
6. **담당 및 연결 유효성:** 담당 활동·키움 연결 상태를 공유하고 담당 재시작/재연결마다 이전 세션 시세를 주문에 사용하지 않도록 구분한다. 고정 담당도 중복 실행 설정 오류를 방지한다.
7. **시세 저장과 알림:** 저장 후 종목별 이벤트를 발행하고 모든 BE의 채널 추가·해제·재연결 후 최신 상태 조회 흐름을 정의한다.
8. **주문 연동:** 접수 임시 수요와 DB 커밋 간 공백, 최초 체결 판단, 시장가 경로, 여러 BE의 중복 체결 방지를 검토한다.
9. **코스피 전환:** 장중 값과 장외 보관 값의 경계, 주말·연휴·재시작 시 복구를 명세한다. 장중 TTL 60초 만료 전에 장외용 값을 확보하는 저장 방식이 필요하다.
10. **두 BE 검증:** 키움 단일 호출 담당, 중복 REST 조회 방지, JSON/TTL, 알림 누락 복구, DB 중복 체결 방지, Redis·담당 장애, 담당 재시작, ACL 거부를 검증한다.

### 전체 코드 검토의 보완 사항

- 별도 검토에서 확인한 중요한 두 경합을 수정했다: 단일 기본 스케줄러의 긴 작업 때문에 담당 TTL 갱신이 밀리는 문제, DB 계좌 잠금 대기 중 연결이 바뀌어도 이전 출처로 체결되는 문제.
- 담당 갱신은 전용 collectorLeaseScheduler로 분리하고 일반 taskScheduler를 별도로 유지한다. 기본 스케줄러를 막은 상태에서 실제 예약된 갱신이 진행되는 회귀 테스트를 추가했다.
- 시장가·지정가 생산 경로는 출처 검증 콜백을 체결 서비스로 전달하고 계좌 잠금·DB 조회 후 자산 변경 직전에 재검증한다. 임대·세션 변경이 생기면 변경을 중단한다. 콜백 없는 기존 직접 호출 생성자/메서드는 격리된 서비스 테스트와의 호환 용도로 유지한다.
- 수정 전 두 테스트 실패를 확인했고 수정 후 통과를 확인했다. 실제 H2 계좌 잠금 대기 후 출처가 무효화된 시장가 요청의 자산 유지도 최종 전체 검증에 포함한다.
- Redis 검증과 DB 커밋 사이의 원자적 차단은 별도 문제로 남는다. 이 수정은 잠금 대기 시간을 지나서도 검증 없이 체결하던 큰 공백을 제거한다.
