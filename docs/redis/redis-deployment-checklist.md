# Redis 전환 배포 준비

현재 구조는 고정 수집 담당 BE 1대와 일반 BE 여러 대가 같은 Valkey와 DB를 사용하는 방식이다. 담당 자동 인계는 없으며 담당 장애 시 새 주문·체결을 중단한다. DB의 대기 주문은 유지한다.

## 인프라 IAM 연결 보완

이후 Serverless Valkey 주소·사용자명·TLS·클러스터·리전·캐시 이름을 전달받았고 인스턴스에 IAM 역할이 부여됐다는 확인을 받았다. 인프라 변수 이름을 그대로 사용하는 [IAM 연결](iam-connection.md)을 구현했다. 아래의 “접속 설정 없음”과 282개 검증 수치는 이전 단계 기록이다. 실제 인스턴스 IAM·MySQL·배포 Valkey 연결 검증은 여전히 별도다.

IAM 보완 후 최종 전체 회귀·빌드·정적 분석이 성공했다. **290개 중 284개 통과, 실제 키움 연결 테스트 6개 건너뜀, 실패·오류 0건**이다. 처음과 주기 갱신의 일시적 실패를 복구하는 테스트까지 포함했으며 기존 로컬 Valkey·ACL·다중 BE·장애 복구·부하를 함께 검증했다. 배포 클러스터 초기화·갱신에 필요한 `CLUSTER NODES`, `INFO` 권한은 인프라 ACL에서 확인한다.

인프라 접속 설정이 아직 없다는 사용자 확인에 따라 [운영 인계](operations-handoff.md), 공통·역할별 환경변수 예시, [PR 설명 초안](pull-request-draft.md)을 준비했다. 배포용 `bootJar` 빌드와 현재 CI의 `spotbugsMain` 정적 분석이 모두 성공했다. `.env.local`은 Docker 빌드 컨텍스트에서도 제외한다. Docker 이미지 빌드·원격 게시·PR 생성·실제 배포는 이번 단계에서 수행하지 않았다. 기존 CD가 사용하는 인프라 저장소의 역할별 서비스·환경변수 반영은 배포 전 필요하다.

## 최신 전체 회귀 검증 — 2026-10-12

REST 3초 대기 상한, 가격 미충족 주문 선검사, 주문·보고서 반복 조회 제거 후 전체 테스트를 실행했다. **총 282개 중 276개 통과, 실제 키움 연결 테스트 6개 건너뜀, 실패·오류 0건**, `BUILD SUCCESSFUL`이었다. 로컬 Valkey ACL·저장소·다중 BE·장애 복구·REST 부하 및 시세·주문 부하를 포함했다.

```powershell
$env:REDIS_LIVE_TEST = 'true'
$env:REDIS_LOAD_TEST = 'true'
$env:REST_LOAD_TEST = 'true'
$env:KIWOOM_REDIS_LIVE_TEST = 'false'
.\gradlew.bat test
```

실제 외부 연결용 `KIWOOM_LIVE_TEST`, `KIWOOM_STREAM_LIVE_TEST`는 설정하지 않은 상태다. 새 PowerShell 세션에서 실행하거나 기존 세션의 해당 변수 값을 확인한다. 사용한 테스트용 변수는 실행 후 제거한다.

최신 실행에서 시세 알림 40개가 두 일반 BE에 각각 수신됐고, 주문 100개는 각각 한 번만 체결됐다. 보유 100주·현금 8,050,000원·담당 활동 유지가 확인됐다. 미충족 단계는 0.767초, 체결 단계는 3.548초였다. REST 100개 동일 TR 요청은 20개 성공·80개 호출 전 거절로 약 3.214초에 처리 종료됐다. 최근 변경의 별도 코드 검토에서도 중대한 결함이 발견되지 않았으며 Redis 문서의 상대 링크는 정상이다.

이 결과는 로컬 검증 완료 기록이다. 실제 키움·BE 세 개·MySQL을 결합한 검증과 배포 Valkey ACL/TLS·네트워크·운영 부하 검증은 남아 있다. 배포 Valkey 주소·TLS·인증 설정이 아직 제공되지 않아 실제 배포 연결 검증은 실행하지 않았다. 이후 절의 수치는 단계별 이전 기록이다.

## 로컬 다중 프로세스 검증 결과 — 2026-10-12

담당 BE 1대와 일반 BE 2대를 별도 JVM으로 실행하는 테스트가 통과했다. 공유 Valkey와 테스트 전용 H2 TCP DB를 사용했고 외부 키움 연결은 가짜 응답으로 대체했다.

- 두 일반 BE의 종목정보 요청은 담당 조회 1회 후 같은 Redis 캐시를 사용했다.
- 두 일반 BE의 REST 요청은 실제 내부 HTTP 인증 경로를 통해 담당으로 전달됐다.
- 두 일반 BE가 시세 알림을 수신했고 공유 주문의 체결 기록은 1건, 현금은 1,000,000원에서 880,500원으로 한 번 차감됐다.
- 담당 중단 후 REST 조회가 거절됐으며 활동 키 정리 후 이전 연결 시세가 사용되지 않았다. 종료 정리를 못하면 활동 TTL 15초까지 감지가 지연될 수 있다.
- 시세 활성화 상태의 서버 시작에서 Redis 알림 컨테이너가 두 개 생기는 문제가 발견되어 시세용 컨테이너를 명시적으로 선택하도록 수정했다.
- Valkey 포함 전체 테스트: 270개 중 265개 통과, 실제 키움 연결 테스트 5개 건너뜀, 실패·오류 0건.

이 결과는 실제 키움·MySQL·배포 Valkey 및 부하 검증을 대신하지 않는다. 재현 명령과 테스트 정리 방식은 [local-valkey.md](local-valkey.md)의 실제 JVM 세 개 검증 항목에 기록했다.

## 추가 시세·주문 부하 검증 — 2026-10-12

추가 시세·주문 부하 검증에서는 별도 JVM BE 3대가 연속 시세 40개를 처리했고, 두 일반 BE가 각각 40개를 수신했다. 같은 계좌의 주문 100개가 중복 없이 각각 한 번만 체결됐으며 보유 100주·현금 8,050,000원을 확인했다. 다만 매수 조건 미충족 단계는 약 34초, 체결 단계는 약 11초로 처리 지연 개선이 필요하다. [시세·주문 부하 측정](quote-order-load-measurement.md)에 범위와 재현 방법을 기록한다. 실제 키움·MySQL·배포 Valkey 결과가 아니다.

후속 개선으로 가격 미충족 주문은 체결 서비스 진입 전에 제외한다. 같은 조건 재측정에서 미충족 단계는 6.746초로 줄었으며 중복 체결 방지·현금·보유 수량은 유지됐다. 체결 단계는 14.908초로 더 오래 걸렸으므로 체결 성능 개선으로 해석하지 않는다. 미충족 주문의 만료 정리는 기존 5초 갱신 주기를 사용한다. 관련 테스트 25개가 모두 통과했으며 전체 테스트 재실행 및 실제 MySQL·배포 환경 검증은 별도다.

추가로 Hibernate 통계에서 주문 20개의 목록·보고서 조회에 SQL 21회가 실행되는 것을 확인했다. 보고서를 목록과 함께 조회하도록 변경한 뒤 같은 부하는 미충족 단계 0.908초·체결 단계 3.459초로 줄었다. 주문별 단일 체결·현금·보유 수량·담당 활동은 유지됐고 관련 테스트 26개가 모두 통과했다. 운영 부하 성능으로 일반화하지 않으며 전체 회귀 및 배포 검증은 여전히 별도다.

## 실제 외부 연결 검증 결과 — 2026-10-12

`KIWOOM_REDIS_LIVE_TEST=true`로 운영 Redis 토큰·담당 활동·시세 저장 구성의 실제 키움 연결 검증 1개가 통과했다.

- 실제 현재가·종목정보·코스피 REST 조회와 종목정보·지수의 Redis 저장 및 공유를 확인했다.
- 실제 WebSocket LOGIN/REG와 서로 다른 시각의 현재가 메시지 2회 이상, 호가 수신을 확인했다.
- 실제 시세의 Redis 저장과 일반 BE 처리 경로의 Pub/Sub 수신을 확인했다.
- 새 토큰 제공자 및 담당 ID를 바꾼 새 인스턴스가 Redis 토큰을 재사용했고 일반 BE 역할은 토큰 접근을 거절했다.
- 테스트 캐시와 담당 활동은 정리했으며 유효한 키움 토큰은 재사용용으로 Redis에 남겼다. 토큰·인증값은 출력하지 않았다.

담당·일반 처리 객체는 한 테스트 JVM에서 구성했다. 앞선 실제 JVM 세 개 검증은 가짜 키움을 사용했다. 실제 키움과 BE 세 개를 결합한 부하, 실제 서버 재시작, MySQL·배포 ACL/TLS 검증은 여전히 남아 있다.

## 장애·복구 검증 결과 — 2026-10-12

BE 세 개의 Redis 연결 장애·복구 테스트와 실제 키움 웹소켓 종료·재연결 테스트가 각각 통과했다.

회귀 검증은 `REDIS_LIVE_TEST=true`, `KIWOOM_REDIS_LIVE_TEST=false`로 전체 272개 중 266개 통과, 외부 연결 테스트 6개 건너뜀, 실패·오류 0건이었다. 실제 키움 재연결 테스트 1개는 별도로 활성화해 통과했다. 이번 단계는 테스트·테스트 실행 설정을 보완했고 운영 코드 변경은 없었다.

- Redis 연결 장애 중 새 주문 접수는 503으로 거절됐고 기존 대기 주문·현금은 유지됐다. DB 기반 상태 조회·취소는 가능했다.
- 잘못된 내부 비밀키는 외부 조회에 도달하지 않았다.
- 연결 복구 후에도 자격을 잃은 담당은 자동으로 재획득하지 않았다. 이전 담당 강제 종료 후 같은 HTTP 포트에서 새 담당을 실행하여 일반 BE 조회 복구를 확인했다.
- 이전 담당·이전 연결 시세는 거절됐고, 새 시세 이후 공유 주문의 체결·현금 차감은 한 번만 발생했다.
- 실제 키움 연결도 정상 종료 후 새 LOGIN/REG와 새 현재가·호가를 수신했으며 같은 담당의 이전 연결 출처는 거절됐다.

Redis 장애는 테스트용 프록시로 BE 연결만 끊어 재현했다. Valkey 서버 자체를 중단하지 않았다. 주문 장애 검증은 가짜 키움과 공유 H2 TCP DB를 사용했고 실제 키움 재연결은 한 테스트 JVM의 처리 객체로 검증했다. 배포 Valkey·MySQL·전체 서버 장애·임의 외부 네트워크 단절·부하 검증은 남아 있다.

## 인프라에 전달할 사항

현재 배포 연결 설정은 미준비이며, 사용자 확인에 따라 로컬 ACL 검증을 먼저 수행했다. 인프라에는 [valkey-acl-requirements.md](valkey-acl-requirements.md)의 키·채널·명령 권한 표와 필요한 연결 정보를 전달한다. 로컬 ACL 검증과 배포 환경 검증을 구분한다.

- 전달받은 Valkey 엔드포인트·TLS·클러스터·IAM 변수를 주입한다. 인스턴스 역할로 토큰을 생성·갱신하며 비밀값을 문서나 Git에 기록하지 않는다. 실제 IAM 접속 권한·사용자 설정·네트워크 경로는 인프라 환경에서 확인한다.
- 기존 허용 키 `quote:*`, `session:*`, `token:*`에 **`coord:*`를 추가**한다. Pub/Sub 채널은 `quotes:*`이며 `PSUBSCRIBE`를 사용하지 않는다.
- 명령 권한은 `GET`, `SET`(NX/EX/PX 포함), `EXPIRE`, `PEXPIRE`, `DEL`, `EVAL`, `EVALSHA`, `SCRIPT LOAD`, `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE`가 필요하다. 연결 초기화 명령까지 포함한 최종 ACL은 실제 Spring/Lettuce 연결로 확인한다.
- 내부 REST 주소는 일반 BE가 접근할 수 있는 담당 BE 주소로 지정한다. 내부 API의 외부 접근을 제한하고 공통 `KIWOOM_COLLECTOR_SECRET`을 비밀 관리 방식으로 주입한다.
- 담당 역할은 인스턴스 한 대에만 부여한다. 담당 역할을 여러 대에 설정하면 활동 키를 이미 가진 서버 외의 시작은 실패한다. 일반 BE만 늘리는 방식으로 구성한다.

## 서버별 설정

| 설정 | 담당 BE | 일반 BE |
|---|---|---|
| `KIWOOM_COLLECTOR_ENABLED` | `true` | `false` |
| `KIWOOM_STREAM_ENABLED` | `true` | `true` |
| `KIWOOM_COLLECTOR_URL` | 생략 가능 | 담당 BE의 내부 HTTP(S) 주소 |
| `KIWOOM_COLLECTOR_SECRET` | 공통 비밀값 | 같은 비밀값 |
| `KIWOOM_APP_KEY`, `KIWOOM_APP_SECRET` | 설정 | 생략 가능 |
| `REDIS_HOST`, `REDIS_PORT` | 공유 Valkey 주소 | 같은 주소 |
| `REDIS_USERNAME`, `REDIS_PASSWORD`, `REDIS_SSL` | 배포 연결 설정 | 같은 저장소에 접근하는 설정 |
| `REDIS_CLUSTER_MODE` | 배포 Serverless는 `true` | 같은 값 |
| `AWS_REGION`, `ELASTICACHE_CACHE_NAME` | IAM 리전·캐시 이름 | 같은 값 |

현재 IAM 배포에서는 `REDIS_PASSWORD`를 사용하지 않는다. 캐시 이름이 비어 있을 때만 기존 로컬/비밀번호 인증을 사용한다.

DB도 공유해야 중복 체결을 계좌 잠금과 주문 상태 검사로 방지할 수 있다. 실제 여러 프로세스로 실행할 때는 각 BE의 서버 포트를 구분한다. 로컬 테스트 기본 Valkey 포트는 6380이다.

## 검증 순서

1. 담당 BE를 켜기 전에 배포 Valkey의 실제 TLS·ACL로 Spring 연결, TTL, Lua, 개별 채널 Pub/Sub를 검증한다. 로컬에서 통과한 결과가 배포 ACL 검증을 대신하지 않는다.
2. 담당 BE 1대와 일반 BE 2대를 같은 DB·Valkey에 연결한다. 일반 BE에서 종목정보를 요청하여 담당 경유·공유 캐시 재사용을 확인한다. 주문 상태 조회는 매번 신선한 REST 조회여야 한다.
3. 두 일반 BE의 주문 수요로 같은 종목을 요청한다. 키움 연결은 담당만 만들고, 일반 BE들은 저장된 시세와 개별 채널 알림을 사용해야 한다. 양쪽이 같은 알림을 받아도 주문 체결·현금 차감은 한 번이어야 한다.
4. 담당 중단, Redis 중단, 내부 비밀키 오류를 각각 검증한다. 새 주문·체결은 실패하고 대기 주문은 DB에 남아야 한다. 일반 BE가 키움에 직접 연결하거나 토큰을 발급하면 안 된다.
5. 담당 재시작 후 새 연결의 첫 시세를 기다리는지 확인한다. 이전 연결의 가격은 주문에 사용하지 않는다. Pub/Sub 재접속은 최신 캐시로 다시 판단하며 중간 이벤트를 재생하지 않는다.
6. 실제 키움으로 현재가·호가 수신, 읽기 전용 REST, 토큰 재사용을 확인한 뒤 부하 검증을 수행한다. 테스트용 가짜 시세/H2 결과와 실제 외부 연결 결과를 구분해 기록한다.

## 아직 결정 또는 확인할 사항

2026-10-12 호출 제한 변경 후 Valkey·REST 부하 포함 전체 테스트 277개 중 271개 통과, 외부 연결 테스트 6개 건너뜀, 실패·오류 0건이었다. 이전과 동일한 네 REST 부하 조건은 모두 성공했다. [변경 후 측정 결과](rest-load-measurement.md)를 참고한다. 실제 키움 부하·배포 검증 결과는 아니다.

- 사용자 확인(2026-10-12): 현재가는 담당·종목 구독·연결 ID를 검증하는 기존 기준을 유지한다. 수신 후 추가 경과시간 제한은 추후 결정하며 이번 단계에서 5초 제한을 추가하지 않는다. 시세 TTL 1일은 정리 기간이며 신선도 보장이 아니다. 호가의 기존 5초 판단은 유지한다. REST는 현재 설정으로 먼저 측정한 뒤 호출 순서 대기 상한 3초를 승인·적용했으며 [대기 부하 측정 결과](rest-load-measurement.md)에 기록했다.
- 사용자가 제공한 공식 FAQ로 실전 REST의 TR당·토큰별 초당 5회 기준을 확인했다. 단일 계좌/토큰의 각 api-id에 최근 1초 최대 5회까지 즉시 허용하고 초과 요청만 기다리도록 변경했다. 응답 후 220ms를 두는 이전 방식은 대체됐다. 이후 사용자 승인으로 호출 순서 대기를 최대 3초로 제한했다. 초과하면 외부 호출 전에 실패하며 내부 조회 API는 503을 반환한다. 전체 HTTP 응답 제한과는 별개다. [공식 확인 기록](kiwoom-call-limit-verification.md)과 [대기 상한 적용 결과](rest-load-measurement.md)를 참고한다.
- 휴장일 달력, 실제 배포 네트워크·부하, 임대 확인과 쓰기 사이 및 최종 시세 확인과 DB 커밋 사이의 원자성은 현재 검증 범위 밖이다.
- 인프라가 제공한 IAM Valkey 설정은 [환경변수 예시](deployment-common.env.example)에 반영했다. 실제 배포 환경의 설정 주입·MySQL 연결·검증 실행은 인프라 환경에서 수행한다. 로컬 `.env.local`을 배포 대상으로 변경하지 않았다.

구현과 로컬 검증의 상세 내용은 [local-valkey.md](local-valkey.md)를 참고한다.
