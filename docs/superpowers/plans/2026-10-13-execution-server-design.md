# 체결 서버 분리 설계

## 목표와 승인된 범위

기존 체결 판단·처리 로직을 유지하면서 BE와 별도 프로세스로 실행한다. 동일 저장소와 공유 MySQL/Redis를 사용한다. BE의 직접 체결 호출은 내부 HTTP로 변경한다. 이번 단계에 SQS와 AI 팀 시세 서버의 미확정 데이터 규격을 도입하지 않는다.

## 실행 진입점 — Application 분리 방식으로 변경

2026-10-13 사용자 요청에 따라 동일 Application의 실행 역할 선택 대신 별도 Application 두 개와 별도 실행 JAR를 사용한다. 구체적인 구현 순서는 [Application 분리 계획](2026-10-13-execution-application-plan.md)을 따른다. 아래 기존 local/api/execution 역할 설명은 책임 구분이며 세 가지 배포 모드를 구현하라는 의미가 아니다.

- local: 기존 통합 실행을 유지하는 개발/회귀 테스트용 역할.
- api: 사용자·계좌·주문·보고서 API 및 주문 접수 수요 관리. 체결 이벤트 리스너는 실행하지 않는다.
- execution: 내부 체결 API, Redis 시세 수신, 대기 주문 최초/후속 판단, 체결 트랜잭션, 대기 주문 구독 복구. 외부 사용자 API는 노출하지 않는다.
- RiverBeApplication과 ExecutionApplication을 각각 시작점으로 하는 별도 JAR를 빌드하고 서로 다른 포트/컨테이너에서 실행한다. 운영 서버의 역할은 시작점으로 결정한다.
- 실행 역할이 api/execution인 경우 Kiwoom 직접 수집은 비활성화한다. 기존 수집 담당 또는 AI 팀 시세 서버를 사용한다. AI 팀 규격이 확정되기 전에는 기존 Redis 시세/수요/유효성 규격을 전제로 한다.

## 호출 흐름

지정가: BE가 기존 검증·시세 수요 확보 후 주문을 저장한다. DB 커밋 후 주문 ID/계좌 ID를 내부 HTTP로 전달한다. 체결 서버가 DB에서 주문을 읽어 최신 시세로 최초 판단한다. BE는 주문 조회 서비스를 통해 응답한다. 최초 판단 요청 실패는 이미 저장된 주문을 실패 주문으로 되돌리지 않는다. 체결 서버의 주기적 대기 주문 점검 및 재시작 복구가 시세 이벤트가 없었던 주문도 재판단하며, 기존 만료·시세 유효성 검증을 적용한다.

후속 지정가: 체결 서버가 Redis 시세 알림을 구독하고 기존 리스너 및 executeLimit 트랜잭션을 실행한다. 중복 이벤트/다중 체결 인스턴스/취소 경쟁은 기존 계좌 잠금 및 주문 상태 재검사로 보호한다. 과거 시세로 새 주문이 체결되지 않는 기존 검증을 유지한다.

시장가: BE가 인증·입력 검증 및 임시 구독 수요 확보 후 요청 식별자와 검증된 사용자/계좌/주문 입력을 체결 서버로 보낸다. 체결 서버가 최신 호가와 보유 자산 평가 가격을 직접 확보하고 기존 executeMarket 트랜잭션으로 주문 생성·현금·보유·체결·보고서를 함께 갱신한다. BE는 반환된 주문 ID로 공유 DB에서 응답을 조회한다.

## 시장가 중복 요청과 통신 실패

- BE에서 내부 호출을 자동으로 무제한 재시도하지 않는다.
- 동일 내부 요청 식별자를 다시 전달하면 동일 주문 ID를 반환한다. 서로 다른 입력에 같은 식별자를 사용하면 충돌 오류를 반환한다.
- Redis 만료/재시작에 영향받지 않도록 공유 DB에 내부 요청 식별자·입력 확인값·결과 주문 관계를 저장한다. 체결 변경과 동일 트랜잭션으로 커밋한다.
- 응답 유실 시 식별자로 완료 결과를 조회한다. 진행 중이거나 결과를 확인할 수 없으면 명시적인 결과 확인 불가 오류를 반환하며 실패 체결로 단정하지 않는다.
- 사용자/AI가 외부 주문 API를 새 요청으로 다시 호출하는 중복 방지는 별도 외부 API 정책이다. 이번 내부 요청 식별자만으로 이를 보장한다고 설명하지 않는다.
- 스키마 변경 SQL을 제공하고 기존 데이터에는 영향을 주지 않도록 별도 테이블을 사용한다. 배포 DB 적용은 인프라 인계 대상이며 실제 적용은 별도 배포 승인 시 수행한다.

## 보안과 설정

- 전용 내부 경로 /internal/execution/**와 X-Execution-Key 헤더를 사용한다. 기존 /internal/kiwoom/** 인증과 별도 경로/필터 순서로 구분한다.
- execution 역할은 비밀키가 없으면 시작에 실패한다. api 역할은 체결 서버 URL/비밀키가 없으면 시작에 실패한다.
- 요청 사용자·계좌 소유권과 자동매매 활성 상태는 체결 서버에서도 재검사한다.
- 공개 API는 execution 역할에서 차단하며 health만 운영 점검에 필요한 범위로 허용한다. JWT 사용자 토큰을 내부 비밀키 대신 받아들이지 않는다.
- URL 검증, 리다이렉트 금지, 연결/응답 제한을 설정한다. 제한 시간은 설정 가능하게 하며 내부 HTTP 실패가 결과 미확정일 수 있음을 API 오류로 구분한다.
- 비밀키·토큰·주문 입력 원문은 로그에 기록하지 않는다.

## 코드 책임

- OrderExecutionService와 OrderExecutionListener의 체결 로직 및 공유 트랜잭션을 재사용한다.
- OrderExecutionListener.response는 OrderQueryService로 이동한다.
- BE 컨트롤러는 역할별 실행 가능한 체결 호출 객체를 통해 local에서는 기존 서비스, api에서는 내부 HTTP를 호출한다.
- execution에서는 시장가 HTTP 요청 처리 및 구독 복구 기능만 추가한다. 사용자 API/로그인 서비스를 체결 서버에서 실행하지 않도록 역할 조건을 설정한다.
- OrderSubscriptionService의 주문 접수 수요와 대기 주문 복구 책임은 역할에 맞춰 활성화한다. BE의 임시 수요 정리와 체결 서버의 PENDING 수요가 이어져야 한다.
- 구독 기능은 여러 역할에서 사용되므로 그대로 execution 폴더로 통째로 옮기지 않는다.

## 검증과 완료 기준

1. 기존 local 모드 주문/계좌/보고서/체결 회귀 테스트 통과.
2. api 역할은 시세 알림을 받아도 DB 체결을 수행하지 않음.
3. execution 역할에서 사용자 API가 차단되고 내부 인증 누락·오류·중복 헤더가 거부됨.
4. 두 프로세스가 공유 DB/Redis로 지정가 최초 판단 및 후속 시세 체결·시장가 체결을 수행함.
5. 동일 시장가 식별자 동시 요청/재전송/응답 유실에도 주문·현금·보유·체결 결과가 한 번만 반영됨.
6. 지정가 내부 호출 실패 후 재시작·주기 점검으로 대기 주문 복구, 취소와 체결 경쟁 및 만료 주문 방어 확인.
7. DB/Redis/체결 서버 장애 시 부분 자산 변경이 없고, 시세 유효성 및 기존 호가 5초 기준을 유지함.
8. 전체 Gradle build/SpotBugs 통과, 실행 설정·SQL·기존 담당/AI 팀 연동 전제·인프라 인계 문서 제공.

## 현재 상태

사용자가 별도 요청 기록 테이블 및 결과 미확정 정책을 승인했다. Application 분리 계획에 따라 제품 코드 구현과 로컬 검증을 완료했다. DB 적용/배포는 수행하지 않았다. 실제 외부 환경 검증은 인프라 인계 문서를 따른다.
